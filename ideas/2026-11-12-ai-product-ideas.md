## 📊 今日核心洞察

### 热点话题

1. **美联航禁止 AI Agent 代客订票——Agent 商业化的第一道墙不是智力，是"准入"**

   今天 HN 首页最热的一条（183 分、188 条评论，评论数远超分数，说明争议极大）：**美联航明确禁止 AI Agent 代表旅客订票。**

   这条新闻要拆成两层看。

   表层是"又一家公司封杀 Agent"。深层是一个结构性问题：**Agent 在技术上已经能完成订票，但在商业与法律上并不被允许完成订票。** 航司的顾虑不是"它做不对"，而是：出了错谁负责？退改签的合同主体是谁？异常行程（超售、航班取消、联程误机）由谁承担？欺诈与占座怎么防？这些问题的答案，航司一个都没有，所以最省事的策略是"一律禁止"。

   这和 2000 年代初期"禁止在网上用信用卡支付"是同构的。当年的解法不是让浏览器更聪明，而是**造出了支付网关、3-D Secure、chargeback 规则和商户协议**——一整套"让机构敢接受"的基础设施。今天 Agent 缺的正是这一层。

   对比一下今天 HN 上另一条同源新闻：**Pomerado（YC F26）"把任何网站变成 Agent 可用的 MCP"**。它的 pitch 里有一句非常诚实的话：Agent 现在的瓶颈不是智能，而是"与系统交互的能力"；而航空、银行、电商、保险、政务这些门户既没有 API 也没有 MCP，Agent 只能靠浏览器自动化或 computer use，**又慢又贵又不可靠；而且就算 computer use 做到完美，大多数公司出于安全和合规也已经禁掉了它。**

   两条新闻拼在一起，今天的核心矛盾就非常清楚了：

   > **Agent 的能力曲线在指数上升，Agent 的准入曲线几乎是平的。** 缺口不在模型侧，在"授权、责任、审计"这一层。

   这不是一个技术问题，这是一个**产品问题**，而且是一个还没人做好、但所有人都会需要的问题。

2. **AWS 用自主 Agent 写出了一个 AWS 模拟器——538 分背后的真问题是"谁来验收"**

   今天 HN 榜首级的一条（538 分、186 条评论）：AWS 官方博客披露，他们用自主 AI Agent 构建了一个 AWS emulator，配套的文章标题更值得玩味——《Agent 写代码时，工程师的工作是什么》。

   这件事的意义不在于"Agent 能写代码"（这已经不新鲜），而在于**它把"验收"这个环节推到了台前**。一个由 Agent 写出来的 AWS 模拟器，行为要和真实 AWS 足够一致，否则所有基于它做的测试都是假阳性。那么：谁定义"一致"？谁生成验收用例？谁判断"足够一致"？谁在 Agent 说"我做完了"的时候，去和真实系统对账？

   HF 上微软那篇《The Agent Said It Was Done. The Database Disagreed.》讲的就是这件事的另一面——**Agent 的自我报告和系统的真实状态之间，存在系统性偏差。** 这不是模型不够强，而是"自我评估"这个机制本身不可靠：它评估的是"我以为我做了什么"，不是"世界实际变成了什么样"。

   所以今天真正稀缺的能力是：**把"世界状态"变成 Agent 可查询、可验证、可对账的东西。** 谁能提供这个"对账层"，谁就握住了 Agent 大规模上岗的闸门。

3. **Agent 评估从"打分"变成"取证"：trace 级评测的 F1 是 0.90，纯文本评测误报率高 5 倍**

   arXiv 今天有一篇相当实用的论文：《Comparative Analysis of Agent Evaluation Frameworks: Stability, Detection, and Discovery in Enterprise Analytics Agents》（KDD 2026）。

   它把企业级 Agent 评测拆成三阶段，并对比了三种范式：**基于执行轨迹的 LLM 评判、纯文本 LLM 评判 + 红队、确定性启发式规则。**

   结论很硬：

   - **稳定性**：97% 的配置达到稳定性阈值，且稳定性与具体 Agent 无关——说明"评测本身"可以作为独立基础设施来做。
   - **已知风险检出**（72 个 ground-truth 用例）：**trace-based 的 F1 达到 0.90**，是最好的精确率/召回率平衡；纯文本评测召回持平，但**误报多 5 倍**。
   - **未知风险发现**：共发现 24 个新失效模式，**功能测试与安全红队的发现零重叠**。

   最后一条最值得产品人警觉：功能和安全的失效集合**几乎不相交**。这意味着"把功能测好"完全不能替代"把安全测好"，反之亦然。论文的建议是双框架并行：trace-based 做功能评估，对抗性红队做安全验证。

   翻译成产品语言：**Agent 的"测试"不是写几个 prompt 跑一遍，而是一条需要被工程化的流水线**——采集轨迹、切片归因、生成回归集、双轨评测、给出可复现的失败证据。今天 99% 的团队还在用"手动试几个 case + 看感觉"的方式验收 Agent。

4. **"决策"被单独产品化：Google 的 Decisions API 与 HF 的 Decision Models 同日出现**

   今天 HN 上 Gemini Decisions API 拿到 178 分；HF 博客在同一天发了《Decision Models in Hugging Face》。两个不同的组织，同一天，把"决策"从"生成"里单独拎出来做成了一个品类。

   这个信号很强。过去两年大家把一切塞进"对话"：决策也是对话的一个输出。但**决策和生成的性质根本不同**——生成要的是多样性、创造性、可编辑；决策要的是确定性、可复现、可解释、可审计、有明确的责任归属。

   一个航班改签决策、一个额度审批决策、一个退款决策，需要的是："在给定策略下，这个输入必然得到这个输出，并且我能说清是哪条规则起的效。" 这跟"帮我写一段文案"是完全不同的产品契约。

   这也解释了为什么企业落地 Agent 卡在"最后一公里"：**企业真正想自动化的不是"生成内容"，而是"做判断"。而做判断需要的不是更大的模型，是决策层的基础设施。**

5. **小模型的成本曲线继续下探：十亿参数以下的端侧 Agent、Token Pooling、华为 MACaQ**

   今天有三条技术信号指向同一个方向——**Agent 的推理成本正在被系统性压低**：

   - **HF / QVAC 的 BotPsy**：一个**十亿参数以下**的端侧个人助理 Agent 模型，跑在设备上。端侧 Agent 从"玩具"进入"可用"区间。
   - **Token Pooling-Aware Training for Multi-Vector Embedding Models**：多向量检索的成本优化，直接关系到 RAG 和记忆系统的单价。
   - **华为开源 MACaQ**（HN 37 分）：面向本地推理的内部量化器。

   把这三条和上面"Agent 准入墙"放在一起，会得到一个有点反直觉的结论：**未来 12 个月，Agent 的"能力成本"会便宜到可以忽略，而"信任成本"会成为账单上的主要科目。** 也就是说，钱会从"推理"流向"验证、审计、责任与合规"。

   这和 2000 年代软件业发生过的事一模一样：计算变便宜之后，值钱的是 SLA、合规认证和保险。

6. **科研 Agent 从"证伪"进化到"区分竞争解释"**

   arXiv 今日的《Contrastive Discovery: Open-Ended Scientific Discovery over Competing Explanations》（NeurIPS 2026）提出了一个很漂亮的观点：现在的 LLM 科研 Agent 大多做**逐点假设检验**——验证 h，如果证据否定 h，就结束。但"否定一个解释"并不等于"找到了正确的解释"。

   它把单一假设换成一个**对照集（contrast set）**：一个科学问题配上若干**互斥且完备**的竞争解释。每个实验的评分标准变成"这个证据把信念在各解释之间如何重新分配"，当信念集中到某一个解释时，问题被解决。

   效果：在六个领域里，逐点方法中"信念位移最大"的候选有 89% 只是被否定；同样的证据，对照集能把其中 73% 归结到某个具体替代解释；用对照集引导搜索，在同等实验预算下**多解决 67% 的问题**。盲测中，38 位人类专家在 78% 的已解决问题上选出了相同解释。

   产品含义：**"给出一个答案"和"在若干可能中确定是哪一个"，是两种完全不同的产品能力。** 后者才是企业真正愿意付钱的——诊断、归因、根因分析、A/B 结论，本质都是"在竞争解释中做区分"，而不是"生成一个看起来合理的说法"。

7. **其余值得扫一眼的方向**

   - **MIT Tech Review**：今天的主线仍是 COP31 与气候金融，其中一条值得注意——COP31 的边会议程里出现了"让 AI 更可持续"的自愿承诺，但文本明确"不产生任何新义务"。这类"表态型治理"越多，越说明**实质性的合规压力会来自采购方而不是监管方**。
   - **GitHub Trending**：Agent 基础设施继续霸榜，网站→API/MCP 类的工具明显增多，和 Pomerado 的方向一致。
   - **arXiv 其他**：医疗影像 foundation model 的跨机构泛化研究（结论是"只需微调极小部分参数，且所需容量由影像域决定而非微调方法决定"），对垂直行业模型的产品化有直接参考价值——**垂直模型的护城河不在参数量，在域适配的取舍策略。**

## 🔍 潜在需求分析

### 需求一：让机构"敢接受" Agent 的授权与责任层

**痛点来源**

美联航封杀 Agent 订票不是孤例。今天 HN 上 188 条评论里，大量从业者在说同一件事：不是我们不想支持，是**我们没有一种方式能确认"这个请求真的是用户授权这个 Agent 做的"**。浏览器自动化留下的请求，在服务端看来和一个脚本攻击没有区别。

**具体场景**

- 旅客让个人助理 Agent 订一张改签机票。航司需要知道：用户是谁、授权范围是什么（只能改签不能退款？预算上限多少？）、这笔操作的凭证能否被验证、出错后向谁追责。
- 企业采购 Agent 代替员工在供应商门户下单。供应商需要同样的东西，且需要"可撤销"。
- 银行场景更极端：任何代客操作都必须留痕、可回放、可举证。

**市场机会**

这是一个**双边基础设施**市场：一边是"想用 Agent 的用户/企业"，一边是"被 Agent 冲击的服务方"。历史上所有这类双边信任缺口，最后都会长出一层中间设施（支付网关、OAuth、eKYC、DocuSign）。

关键判断：**这件事不会由单个服务方解决**（航司没有动力为所有 Agent 厂商做适配），**也不会由单个 Agent 厂商解决**（没有服务方会相信竞争对手的授权声明）。中立第三方是唯一可行位置。

商业模式上，这是典型的"按验证次数收费 + 企业年费"的生意，且天然具备网络效应：接入的服务方越多，Agent 厂商越必须接入；反之亦然。

### 需求二：Agent 上线前的"评测流水线"，而不是评测报告

**痛点来源**

今天那篇 KDD 论文给出的数字本身就是痛点：trace-based 评测 F1=0.90，纯文本评测误报高 5 倍，功能与安全失效零重叠。但现实是，绝大多数团队既没有 trace 采集，也没有回归集，更没有红队。

更麻烦的是**评测的时效性**：Agent 的行为会随着模型版本、prompt、工具集、上游 API 的变化而漂移。一次性评测报告在交付那一刻就开始过期。

**具体场景**

- 一个客服 Agent 每周改一次 prompt。改完怎么知道没退化？现在靠"上线后看投诉"。
- 一个数据分析 Agent 接了 12 个工具。某个工具的返回格式变了，Agent 开始静默给出错误答案——**不报错，只是错。**
- 采购方要求提供"Agent 可靠性证明"，团队拿不出任何可复现的材料。

**市场机会**

这本质上是一个 **CI/CD 品类**：Agent 的回归测试、灰度、金丝雀、回滚。参照 DevOps 的演进路径，测试与可观测性最终会长成比"开发工具"更大的市场。

切入点是"**从生产 trace 反向生成测试集**"——这是 Agent 特有的、传统测试没有的能力，也是数据飞轮所在：用得越多，回归集越全，迁移成本越高。

### 需求三：把跑通的 Agent 轨迹"编译"成廉价工作流

**痛点来源**

今天 arXiv 的《ReTrace: Distilling Tool-Using Agents into Planner-Free Workflows》点出了一个被普遍忽视的成本结构：**绝大多数生产环境里的 Agent 调用，是在重复执行已经被验证过无数次的固定路径，但每一次都要重新"规划"一遍。**

规划是最贵的那部分——多轮思考、工具选择、错误恢复，token 消耗可能是实际执行的 5-10 倍。而这条路径 99% 的情况下是一样的。

**具体场景**

- 电商客服的"查订单→判断是否符合退款条件→发起退款"三步流程，每天跑 20 万次，每次都让大模型重新想一遍怎么做。
- 财务的"读取发票→校验税号→录入系统"，规则明确，但输入格式有几十种变体。
- 内部报表的"取数→对齐口径→生成图表"，步骤固定，参数变化。

**市场机会**

这是一个**直接对着毛利说话**的产品：把 Agent 的月度推理账单砍掉一个数量级，价值可以用 CFO 能理解的语言表达。

而且它天然是"渐进式"的：先观测、再识别高频路径、再编译、再验证等价性、再切流。每一步都能独立交付价值，非常适合做 PLG。

### 需求四：端侧"个人事务 Agent"的消费级入口

**痛点来源**

BotPsy 这类十亿参数以下的端侧 Agent 模型出现，意味着"在手机上跑一个能干活的 Agent"在算力上已经成立。但端侧真正的卖点不是省钱，是**数据不出设备**——邮件、日程、聊天记录、健康数据，这些是用户绝不愿意上传的东西，也恰恰是"个人助理"最需要的数据。

**具体场景**

- 一个能读你全部邮件、日历、聊天记录的助理，帮你安排行程、跟进事项、起草回复——但所有推理在本地完成。
- 出差场景：航班变动时自动重排整个行程，涉及护照、签证、酒店、报销政策，全部本地处理。
- 隐私敏感职业（律师、医生、记者）的个人信息整理。

**市场机会**

平台厂商（Apple / Google）一定会做通用版本，但它们不会做**垂直深度**和**跨平台**。创业公司的机会在两处：一是极窄场景做到极深（比如"只服务律师的案卷助理"），二是跨平台（iOS + Android + 桌面 + 自托管）。

定价上，端侧产品有一个独特优势：**边际成本接近零**，所以可以做"一次性买断 + 可选订阅"，这在订阅疲劳的当下是差异化卖点。

## 🚀 新产品创意

### 创意一：AgentPass —— Agent 的"授权凭证 + 行为审计"网关

**产品定位**

面向"被 Agent 访问的服务方"和"派遣 Agent 的一方"之间的中立信任层。一句话：**让服务方能够安全地说"是"，而不是只能一律说"不"。**

可以理解为"Agent 时代的 OAuth + 支付网关 + 行车记录仪"。

**核心功能**

1. **授权凭证（Grant）**
   用户在自己的 Agent 里生成一份结构化授权：主体身份（可验证凭证）、被授权方（Agent 的身份与版本指纹）、动作范围（可改签/不可退款、金额上限、时间窗口）、单次/多次、可撤销。签发后是一个签名令牌，服务方离线可验。

2. **代客身份断言**
   请求到达服务方时，携带 `AgentPass-Grant` 头。服务方 SDK 做三件事：验签、检查范围是否覆盖本次动作、检查是否已被撤销。整个过程不需要服务方理解任何 Agent 框架。

3. **行为账本（Ledger）**
   每一次被授权的动作写入一条不可篡改的记录：谁授权、哪个 Agent、什么动作、结果如何、涉及金额。争议发生时，双方看到的是同一份账本。

4. **责任分层模板**
   预置常见场景的责任划分（"授权范围内、Agent 执行正确、服务方系统错误"→服务方担责；"超出授权范围"→Agent 方担责），把法律谈判变成选择题。这是最不起眼但最能促成签约的部分。

5. **撤销与熔断**
   用户一键撤销全部授权；服务方可按主体/Agent/动作类型设置速率与金额熔断；异常模式（同一 Agent 高频试探）自动降级到人工。

**技术实现**

- 凭证格式：基于 SD-JWT / Verifiable Credentials 的裁剪版，支持选择性披露（不必暴露用户全部身份信息，只暴露服务方需要的最小集合）。
- 签名与信任根：AgentPass 作为信任根签发短期证书，服务方只需内置一个根公钥；支持离线验签，避免把网关做成单点故障。
- 部署形态：服务方侧提供一个 20 行的 SDK / 一个 sidecar，不改业务逻辑；Agent 侧提供 SDK 和一个"授权 UI 组件"。
- 账本：初期用 append-only 的签名日志（可用现成的 transparency log 方案），不碰区块链——这个场景要的是"可验证"，不是"去中心化"。
- 隐私：账本只存动作元数据与哈希，不存业务内容。

**MVP 范围（8-10 周）**

- 只做**一个垂直场景**：差旅（机票 + 酒店）。因为封禁事件就发生在这里，痛点最锐利，且动作类型有限（查询、预订、改签、取消）。
- 只做**读 + 两类写**：查询订单、改签、取消。预订涉及支付，先不做。
- 交付物：一个服务方 SDK（Node/Python）、一个 Agent 侧 SDK（TS）、一个授权 UI（可嵌入）、一个账本查询页。
- 冷启动：先找 2-3 家**中型航司/TMC**做设计伙伴。大航司决策链太长，创业公司等不起；中型玩家的差异化诉求更强。

**定价策略**

- 服务方：按验证次数阶梯计价，前 10 万次免费（降低接入摩擦），之后 $0.002/次；企业版按年费 $30k 起，含责任模板定制与 SLA。
- Agent 侧：免费（必须免费，否则 Agent 厂商没有动力接入）。
- 抽成不做。这个生意的基础是"中立"，一旦抽成就变成了交易对手，信任根基就没了。

**为什么现在做**

三个条件今天同时成立：(a) Agent 真的能完成交易了，封禁才开始出现；(b) 端侧 Agent 让"个人派遣 Agent"成为大众场景；(c) 垂类"MCP 化"工具（如 Pomerado）正在把"能访问"变成商品，那么"被允许访问"就必然成为下一个瓶颈。

**主要风险**

平台厂商（Google/Apple）可能推出自己的授权标准。应对：早期就开源凭证格式与验证库，把"中立性"变成护城河，让平台厂商采用比替换更划算。

### 创意二：TraceCI —— Agent 的评测流水线（"Agent 的 GitHub Actions"）

**产品定位**

把今天那篇 KDD 论文的方法论做成产品：**从生产环境的执行轨迹自动生成回归测试集，对每次 Agent 变更做双轨评测（功能 trace-based + 安全红队），输出可复现的失败证据。**

一句话：**让 Agent 的每一次改动，都像代码合并一样有 CI 把关。**

**核心功能**

1. **轨迹采集与归一化**
   SDK / 代理层接入，采集完整执行轨迹：输入、模型调用（含 prompt 与参数）、工具调用与返回、中间状态、最终输出、耗时与成本。归一化成统一的 trace 结构，屏蔽不同框架（LangGraph / 自研 / OpenAI Agents / MCP）的差异。

2. **失败归因切片**
   把一次失败定位到具体环节：是检索没召回、是工具参数错、是规划跳步、还是模型幻觉。这是整个产品的技术核心——**"哪一步错了"比"这次错了"有价值 100 倍**，因为只有前者能变成修复动作。

3. **回归集自动生成**
   从生产 trace 里挖掘边界样本：低频路径、异常输入、曾经失败过的 case、人工接管过的 case。自动脱敏、自动聚类去重，生成可版本化的测试集。**这是数据飞轮：客户用得越久，回归集越值钱。**

4. **双轨评测**
   - 功能轨：trace-based LLM 评判（对齐论文里 F1=0.90 的范式），带 rubric 与证据引用，每个判定必须指向轨迹中的具体片段。
   - 安全轨：对抗性红队，自动生成越权、注入、诱导、数据外泄类攻击，独立计分。
   - 输出一份"变更影响报告"：哪些用例退化、退化在哪一步、是否触及安全边界。

5. **门禁与灰度**
   接入 CI（GitHub Actions / GitLab CI）：评测不达标则阻断合并；达标则按比例灰度，对比线上指标（任务成功率、人工接管率、单次成本）。

6. **可复现的失败包**
   每个失败用例导出一个"可重放包"：固定输入 + mock 的工具返回 + 期望行为。开发者本地一条命令复现。**这一条决定了产品是"报告工具"还是"工程工具"。**

**技术实现**

- 采集层：OpenTelemetry 语义约定扩展（GenAI semantic conventions 已有雏形），用 OTel 而不是自造协议，是为了能接客户已有的可观测性栈。
- 评判层：rubric 驱动的 LLM judge + 确定性断言混合。能用规则判的绝不用模型判（省钱且稳定），模型只判"语义正确性"这类规则无法表达的部分。
- 归因：把 trace 建成 DAG（节点=步骤，边=数据依赖），失败从终点反向传播定位到最小可疑子图。这是把"调试"变成图算法。
- 红队：模板库 + 变异生成 + 领域适配。初期人工沉淀 200 条高质量攻击模板，比纯自动生成有效得多。
- 存储：trace 是写多读少的大对象，用对象存储 + 列式索引（ClickHouse/DuckDB），不要塞进 Postgres。

**MVP 范围（10-12 周）**

- 只支持**一个框架**：优先 MCP + Function Calling 的原生实现（覆盖最广，且不绑定某一家）。
- 只做**功能轨**：红队留到 v2（红队售前故事好听，但交付重、误报多，早期容易翻车）。
- 只做**离线评测**：不做线上灰度（灰度需要改客户的部署架构，早期阻力太大）。
- 交付形态：CLI + GitHub App + 一个 Web 报告页。
- 设计伙伴：3 家已经在生产跑 Agent 的团队（客服/数据分析方向），用他们的真实 trace 打磨归因准确率。

**定价策略**

- 免费版：1 个项目、每月 500 条 trace 评测。目的是让开发者先跑通"改一次 prompt 就知道有没有退化"的爽点。
- Team：$299/月，含 5 万条 trace、CI 集成、回归集版本管理。
- Enterprise：$30k-80k/年，含私有部署、自定义 rubric、审计报告导出（这一项是给采购方看的，往往比技术功能更能促成签单）。
- 关键定价逻辑：**按"评测次数"而不是"seat"收费**，因为价值随 Agent 变更频率增长，而变更频率和人数无关。

**为什么现在做**

论文已经把方法论验证完（trace-based 显著优于 text-only，且功能与安全失效零重叠），工程上没有任何未解难题，缺的只是把它产品化。同时，"Agent 上线后静默出错"正在成为普遍事故类型，采购方开始要求可靠性证明——需求侧的时间窗口已经打开。

**主要风险**

- **客户不愿给 trace**：trace 含敏感业务数据。解法：支持"数据不出域"的本地 runner，只上传指标与哈希。
- **被可观测性厂商吞掉**：Datadog/LangSmith 这类玩家一定会往这个方向走。解法：往"评测与门禁"做深（CI 集成、回归集资产、责任报告），而不是往"看板"做——看板是他们的强项，别硬碰。

### 创意三：Loopcast —— 把 Agent 轨迹编译成确定性工作流

**产品定位**

**观测你的 Agent 跑了什么 → 找出高频且已稳定的路径 → 编译成不带规划的确定性工作流 → 在保持效果的前提下把成本砍一个数量级。**

一句话：**Agent 负责探索，编译产物负责量产。**

**核心功能**

1. **路径挖掘**
   从 trace 里聚类出高频执行路径。判定"可编译"的条件很严格：工具序列稳定、分支条件可枚举、输入 schema 明确、历史成功率高。**不满足就明确告诉用户"还不能编译"——这个"拒绝"能力是产品可信度的来源。**

2. **轨迹编译**
   把选定的轨迹编译成一个显式的工作流（DAG）：节点是工具调用或轻量模型步骤，边是数据依赖，分支是可判定的条件表达式。原来需要"每次重新规划"的部分，变成一次性的结构。

3. **局部保留智能**
   这是关键设计：**不是把所有步骤都变成死规则。** 对"格式千变万化但语义简单"的步骤（如从发票里抽字段），保留一个小模型节点；对"规则明确"的步骤，用确定性代码。每个节点标注"是否需要模型"，并给出成本/准确率权衡。

4. **等价性验证**
   编译后必须证明"和原 Agent 行为一致"。用历史 trace 做回放对比：同样的输入，输出是否在容差内一致。不一致的样本自动进入人工审查队列。**没有这一步，没人敢切流。**

5. **渐进切流与回退**
   按流量比例灰度。线上监控成功率与成本；一旦超出阈值自动回退到原 Agent。用户随时可以"重新探索"——环境变了就重新采轨迹、重新编译。

6. **成本账单对照**
   一页纸告诉 CFO：编译前每月 $X，编译后 $Y，节省 Z%，以及"哪些路径还没编译、为什么"。

**技术实现**

- trace → DAG：从执行轨迹构建数据流图，做节点合并（相同工具 + 相同参数模板）与控制流结构化（把重复出现的分支模式识别成 if/else）。
- 条件表达式合成：从历史样本里归纳分支条件，用决策树 + LLM 辅助命名，产出人类可读的规则（"金额 > 500 且客户等级 != VIP"），而不是黑盒分类器。
- 代码生成：目标不是自研 DSL，而是生成 **Python/TypeScript 代码**（可直接进客户的仓库、可 review、可测试）。这一点极其重要——客户要的是"能带走的资产"，不是"锁在你平台里的配置"。
- 执行引擎：Temporal / 自研轻量调度器，支持重试、超时、幂等。
- 验证：回放引擎 + 差异检测（结构化 diff，而非文本 diff）。

**MVP 范围（8-10 周）**

- 只支持**只读类工作流**：查询、检索、汇总、报表。写操作涉及副作用与幂等，风险高，v2 再做。
- 只做**一个垂直**：电商/客服的订单查询与售后判定。路径短、频次高、ROI 好算。
- 不做自助式产品，先做**服务化的编译器**：客户给 trace，团队半自动编译，交付代码 + 验证报告。用服务换学习，等模式稳定再产品化。
- 目标指标：单条路径成本下降 ≥70%，行为一致率 ≥99%（在回归集上）。

**定价策略**

- 初期（服务模式）：按项目收费，$20k-50k/条路径（含编译 + 验证 + 交付代码），承诺"省不下来不收费"。
- 产品化后：按"节省的推理成本"分成 20-30%，或 $2k/月起 + 按编译路径数计价。
- 分成模式在这个场景特别合适：**ROI 可以直接从客户的云账单里读出来**，不需要客户相信你的 ROI 测算。

**为什么现在做**

ReTrace 这类研究证明了"把 planner 蒸馏掉"在技术上可行；同时企业的 Agent 账单已经从"可以忽略"变成"需要向 CFO 解释"的科目。当成本压力从工程师转移到财务，能直接砍账单的产品就会拿到预算。

**主要风险**

- **环境漂移让编译产物快速过期**：上游 API 改一个字段，整条路径失效。解法：把"漂移检测"做成核心功能（schema 变化监控 + 自动重编译），把风险变成订阅理由。
- **客户觉得"那我不如直接写代码"**：这确实是真实质疑。回答是：客户不知道自己该写哪条路径——**发现"哪 20% 的路径吃掉了 80% 的成本"，本身就是产品价值。**

## ⚠️ 反向思考：今天这些判断可能错在哪

**一、"准入墙"可能被高估。**
如果平台厂商（Apple / Google）在系统层就把"代客操作"的授权做掉了，第三方网关的空间会被压得很窄。这个风险不低——参考 Apple Pay 对第三方支付的处理方式。**应对：不要做"通用授权"，要做"跨机构责任划分"，这是平台厂商最不愿意碰的部分（因为它需要和每个服务方谈法律条款）。**

**二、"评测"可能不是独立品类，而是功能。**
可观测性厂商把它做成一个 feature 是大概率事件。独立产品要活下来，必须拥有"资产"——回归集、rubric 库、行业失效模式库。**卖工具会被吞，卖数据资产不会。**

**三、"轨迹编译"的适用面可能比想象中窄。**
真实业务里，稳定到可以编译的路径可能只有 30-40%，剩下的长尾仍然需要 Agent。但这 30-40% 往往承担了 70% 以上的调用量——**所以商业上依然成立，只是叙事不能吹成"取代 Agent"。**

**四、今天的信号有明显的"美国中心"偏差。**
美联航、YC、AWS、Google 都是美国语境。中国市场的差异在于：平台（微信/支付宝/美团）本身就是超级入口，Agent 的"准入"问题会以"平台开放能力"的形式出现，而不是"航司封禁"的形式。**同样的需求存在，但产品形态会不同——大概率是"平台内 Agent 的服务商认证体系"，而不是跨机构凭证网络。**
