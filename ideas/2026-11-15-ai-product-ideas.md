## 📊 今日核心洞察

### 热点话题

1. **Hacker News 今日第一爆款不是模型，而是一次数据泄露：Lovable 生成的 200 多个应用把护照扫描件和 20 万条私信暴露在公网**

   今天 HN 首页 540 分、198 条评论的那篇调查，标题很朴素——《Lovable 应用暴露了护照信息和超过 20 万条私人消息》。内容一点都不朴素：研究者发现，一批用 AI 无代码平台搭建并已上线运营的应用，把数据库直接开在了公网可读的接口上，里面是用户的护照照片、身份证明、私信记录。

   评论区最扎心的一条大意是：**"这些不是黑客攻破的，是它们本来就没锁门。"**

   这件事的意义远超"又一个 AI 安全事故"。它标志着一个结构性的转折：**过去，做一个能上线的应用需要一支知道"什么该锁"的团队；现在，任何人都能在一下午做出一个功能完整的 SaaS，但没有人告诉他哪些门必须锁。** 平台把"构建"这件事的成本压到了近乎零，却没有把"安全"这件事同步交付出去。

   更麻烦的是责任链条。创始人会说"这是平台生成的默认配置"，平台会说"我们只提供工具，用户要为自己的应用负责"，用户只会说"我把护照传给你们了"。三方的责任是断开的，而断口正好落在最没有专业能力的那一方身上。

   这不是 Lovable 一家的问题。Bolt、v0、Replit Agent、Cursor 一键部署——所有"从想法到线上"的路径都走在同一条钢索上。**AI 让软件供给爆炸，但审计软件的供给没有增长，这个缺口就是今天最确定的市场。**

2. **LinkedIn 和 Monster 一次下架 1000 多个假职位——招聘诈骗已经从"骗钱"进化成"骗身份"**

   同一天 HN 上另一条 148 分的新闻：CBC 调查之后，LinkedIn 与 Monster 合计下架了超过 1000 条虚假招聘信息。

   值得注意的是诈骗手法的变化。早期的假招聘是收"培训费""押金"，靠贪念骗钱；现在的假招聘是**收集简历**——一份简历里有姓名、电话、邮箱、住址、历任雇主、证件号后四位、有时还有身份证照片。这些数据在暗网上的价格远高于一次几百块的"押金"。

   而对求职者来说，判断一条 JD 是真是假，成本高得离谱：要查公司工商信息、要看域名注册时间、要判断 HR 用的是企业邮箱还是 Gmail、要在脉脉上找在职员工核实。**每一个求职者都在重复做同一套尽调，而且大多数人不具备做这套尽调的能力。**

   这是一个典型的"信息不对称 + 高频重复劳动"的组合，也正好是 AI 最擅长吃掉的场景。

3. **IRS 把免费报税系统 Direct File 的代码开源到了 GitHub——"用 Agent 代替人提交正式表单"的最后一块拼图出现了**

   GitHub 上 `IRS-Public/direct-file` 今天在 HN 拿到 129 分。这条新闻表面上讲的是政府透明和开源，但产品含义在别处：**一个国家的税务系统，把自己的表单逻辑、校验规则、提交流程全部公开成了可读的代码。**

   这意味着什么？意味着"AI 帮你填表"这件事，第一次有了**可验证的对照标准**——你的 Agent 填得对不对，不是靠模型自信，而是可以跑一遍官方的校验逻辑。

   过去两年所有的"AI 表单助手"都卡在同一个地方：填得挺像，但没人敢真的点提交。因为表单是有法律后果的，错一格可能意味着罚款、拒签、报销失败。**Agent 可以生成内容，但没有人敢让 Agent 按下那个提交按钮。**

   现在这个问题有了新的解法方向：不是让模型更准，而是让**执行过程可审计**——每一步填了什么、依据是什么、和官方规则是否一致，全程留痕、可回放、可追责。这才是"Agent 进入正式流程"的门票。

4. **Hugging Face 这周的三个信号连起来看：llama.cpp v1.0.0、BotPsy 端侧助手、LLMON 原生标记语言——端侧在收敛，格式在标准化**

   HF 博客这周的三篇文章值得放在一起读：

   - **llama.cpp v1.0.0**：本地推理的接口终于稳定了，端侧从"实验"进入"可维护工程"。
   - **BotPsy**：不到 10 亿参数的模型做端侧个人助理 agent，证明了"小模型 + 好编排"在很多任务上够用。
   - **LLMON（LLM-Native Markup Language）**：IBM 在 Granite 4.1 里推的一种"给模型读的标记语言"，让模型输出结构化内容时不用再和 JSON 的括号搏斗。

   前两件事昨天已经讨论过（端侧交付流水线），第三件 LLMON 是新的、而且更被低估：**当模型开始直接输出"界面"而不是"文本"，就需要一层新的东西来渲染和校验它。** 今天所有的 Agent 产品都在做同一件苦力活：让模型输出 JSON，然后用一堆 try/except 去兜住它偶尔漏掉的引号。这是一个不值得每个团队都自己做一遍的脏活。

   端侧收敛 + 格式标准化，指向同一个结论：**AI 应用的竞争，正在从"模型能力"下移到"工程中间层"。**

## 🔍 潜在需求分析

### 需求一：vibe-code 应用的"上线前闸门"——没人愿意做，但每个人都需要的安全基线

**痛点来源**

Lovable 事件最刺眼的地方在于：这些应用不是被攻破的，是**默认就没锁**。而这类"没锁"的问题，恰恰是最容易自动化发现的一类——数据库没开行级权限、存储桶是 public、API 路由没做鉴权、管理后台和用户页在同一个端口、密钥被硬编码在前端 bundle 里。

这五类问题覆盖了绝大多数 vibe-code 泄露事故，而且每一类都有成熟的检测手段。**问题的本质不是"检测很难"，而是"没人被安排做这件事"。**

传统团队里，这件事由安全工程师或资深后端在 code review 时兜住。而在 AI 生成的团队里，这个角色根本不存在——创始人可能就是唯一的"技术负责人"，而他的技术背景可能是产品经理。

**具体场景**

1. **非技术创始人上线第一个付费产品**：应用跑起来了，第一批用户注册了，开始收钱了。此刻最危险——有真实数据了，但没人检查过数据边界。
2. **融资尽调**：投资人做技术尽调时，第一件事就是扫一遍数据暴露面。一次扫描发现 public bucket，估值谈判直接崩掉。
3. **接企业客户**：To B 采购的安全问卷动辄 200 项。创始人根本答不上来"你们的数据库有没有开 RLS"。
4. **被平台默认配置坑**：Supabase、Firebase 的默认配置是"能跑"，不是"安全"。而 AI 生成的代码会精确地使用这些默认值。

**市场机会**

这是一个**付费意愿极高、替代方案极弱**的市场。逻辑很简单：

- 保险行业已经证明了这条路径。网络安全保险的核保需要技术评估，而目前评估成本高到只有大企业做得起。如果能把这个成本压到 99 美元一次，就打开了一个全新的长尾市场。
- 合规正在强制化。欧盟 CRA（网络韧性法案）已经从"建议"变成"义务"，2027 年起对含数字元素的产品有强制安全要求。**合规是比"安全意识"可靠一万倍的付费驱动力。**
- 与其做"给开发者的工具"（开发者会白嫖开源），不如做"给创始人的保险单"（创始人买的是安心和被免责）。

关键洞察：**不要卖扫描报告，卖"可交付的安全状态"。** 报告没人看，一个"已加固"的徽章、一份可以直接发给企业客户的 PDF、一条接进 CI 的门禁，才是有人付钱的东西。

### 需求二：求职者侧的"职位真实性验证"——把尽调从人肉搬到实时

**痛点来源**

假职位诈骗的核心不是"骗子太聪明"，而是**验证成本的不对称**：骗子发一条 JD 的成本是 0，求职者验证一条 JD 的成本是 20 分钟。

更糟的是，平台方的激励是错位的。招聘平台的收入来自"发布职位数"，下架假职位对它是成本不是收益。CBC 的调查能推动下架 1000 条，说明平台有能力识别，只是没有动力天天做。

**这个缺口只能由站在求职者一侧的产品来填。**

**具体场景**

1. **海投阶段的批量筛查**：一个求职者一周可能看 50 条 JD。逐条查工商、查域名、查邮箱后缀，不现实。
2. **面试前的最后确认**：已经聊到发 offer 了，对方要求提供身份证照片做"入职背调"。此刻是最危险的时刻——沉没成本最高，警惕性最低。
3. **应届生与转行者**：最缺乏判断力、最容易被"高薪 + 低门槛"击中的人群，也恰好是最愿意为安全感付费的人群。
4. **海外求职**：跨境求职者根本无法判断一家境外公司是否真实存在。

**市场机会**

三条可行的商业化路径，按可行性排序：

- **浏览器插件 + 订阅**（C 端，9.9 元/月）：在 LinkedIn、Boss 直聘、Indeed 的 JD 页面上直接给出"可信度评分"。冷启动靠公开数据（工商登记、域名 WHOIS、DNS、企业邮箱 MX 记录、历史招聘数据）。
- **B 端反查**（更赚钱）：把同一套能力卖给招聘平台做"发布前审核"，或者卖给背调公司。平台自己没有动力做，但监管压力来了就有。
- **与保险/法律援助打包**：求职者被骗后最需要的是"怎么维权"。把验证 + 维权指引 + 法律援助打包，客单价可以拉到百元级。

风险要说清楚：**这个品类的天花板受限于"误判成本"**。把一家真公司标成"可疑"，比漏判更伤害信任。所以产品形态必须是"给出证据和疑点"，而不是"给出判决"。

### 需求三：Agent 提交正式表单的"可审计执行层"——不是填得对，而是错了能查、责任能分

**痛点来源**

IRS 开源 Direct File 这件事，把一个长期被绕开的问题摆到台面上：**当 Agent 代替人完成一件有法律后果的事，出了错谁负责？**

目前的 Agent 产品全部止步于"生成草稿"。原因不是能力不够，而是**无法证明它做对了**。一个填错的社会保险号、一个选错的申报身份、一个漏掉的抵扣项，后果都是钱和法律责任。用户不敢点提交，产品就永远停在"建议"这一层。

而"可审计"这件事，恰好是可以工程化解决的：**把 Agent 的每一步决策变成一条可回放的记录，并和权威规则做逐条比对。**

**具体场景**

1. **个人报税**：这是最典型的场景。表单字段多、规则明确、后果直接、每年重复一次。
2. **签证与移民材料**：DS-160 有几十页，一个字段填错就是拒签。而申请人往往要填三四遍。
3. **企业报销与发票合规**：财务审核的本质就是"逐条比对规则"，这正是 Agent 最擅长但最不敢碰的部分。
4. **政府补贴/资质申报**：中小企业每年要填的各类申报表，规则复杂、窗口期短、代办费高。

**市场机会**

这个方向的商业逻辑和"AI 表单助手"有本质区别：

- **卖的不是效率，是"责任的可分割性"。** 传统代办（会计师事务所、签证中介）之所以能收几千块，收的就是"错了算我的"。如果 Agent 能提供同样级别的留痕与追溯，就能切入这块存量市场。
- **切入口要选"规则公开 + 后果明确 + 高频"的场景。** 报税完美符合：IRS 开源了规则、错了要罚款、每年一次。
- **变现阶段可以卖"成功费"而不是"订阅费"。** 报税、签证、补贴申报都是结果导向的，用户对"按结果付费"的接受度远高于按月订阅。

真正的壁垒不在模型，而在**规则库的持续维护**。税法每年变、表单每年改，谁能把"规则版本化 + 变更追踪"做扎实，谁就有护城河。这也是一个越做越重的活，恰好能挡住纯套壳玩家。

### 需求四：LLM 原生输出格式的"渲染 + 校验"中间层——每个 Agent 团队都在重复造的脏活

**痛点来源**

LLMON 这类"给模型读的标记语言"出现的根本原因，是**JSON 不是给模型设计的**。模型生成 JSON 时要额外消耗 token 去维护括号、引号、逗号这些对语义毫无贡献的字符，而这些字符恰恰是最容易出错的部分。

今天所有做 Agent 产品的团队，都在自己的代码里维护着一坨屎山：`try: json.loads() except: 正则兜底 → 再失败就重试`。这段代码每个人写一遍，每个人写得都不太一样，每个人都被它坑过。

更麻烦的是**流式输出**场景。用户要看到内容一点点出现，但 JSON 在解析完成之前是不合法的。于是又要在"流式的 UX"和"结构化的正确性"之间做妥协——大多数产品的解法是"先流式输出纯文本，等结束了再解析一遍"，于是用户看到的内容会突然跳变。

**具体场景**

1. **Agent 输出直接渲染成 UI**：模型返回一个"表单"，前端要渲染成可交互组件。JSON Schema 能描述结构，但描述不了"这个字段该用什么控件"。
2. **多 Agent 之间的消息传递**：Agent A 的输出是 Agent B 的输入。格式错了整个链路就断了，而且很难定位是哪一环出的问题。
3. **流式结构化输出**：聊天界面里要一边出字一边填充卡片，这是目前体验最好的交互形态，也是工程上最难的。
4. **人工审核界面**：结构化输出需要被人类逐字段确认，需要一个"高亮差异 + 单字段编辑"的渲染层。

**市场机会**

这是一个典型的"中间件"机会，特点是**单客户价值不高，但客户数量极大、切换成本高**：

- 所有做 Agent 的团队都是潜在客户，而且他们的痛点完全一致。
- 一旦接进生产链路，替换成本很高（要改所有 prompt 和解析逻辑）。
- 开源核心 + 托管服务是标准打法：开源解析器和渲染器建立标准，托管服务卖"校验规则库、可观测性、多模型适配"。

风险也很清楚：**这类中间件很容易被框架吞掉**。Vercel AI SDK、LangChain 都在往这个方向长。所以切入口必须是它们不愿意做的部分——**跨模型的格式一致性测试和回归**。这是一个苦活，但正好是框架方最不愿意背的。

## 🚀 新产品创意

### 创意一：VibeGuard —— AI 生成应用的"上线前安全闸门"

**产品定位**

一句话：**给用 AI 做出来的应用，做一次"能不能上线"的体检，并自动修好。**

不做通用安全扫描器（那是 Snyk、Semgrep 的地盘），只做一件事：**检测 AI 生成代码里最高频、最高危、也最容易自动修的那几类数据暴露问题**。定位不是"安全工具"，是"上线流程里的一个红灯"。

目标客户非常明确：用 Lovable / Bolt / v0 / Cursor 做出产品、正在收第一批用户钱的独立开发者和 5 人以下团队。

**核心功能**

1. **五类高危暴露检测**（覆盖 80% 的真实事故）
   - 数据库表是否开启行级权限（Supabase RLS / Firebase Rules）
   - 存储桶是否 public 可读（S3 / GCS / Supabase Storage）
   - API 路由是否存在未鉴权的写接口
   - 前端 bundle 中是否硬编码了 service_role key / 私钥
   - 管理后台路由是否与用户路由共用同一套鉴权

2. **一键修复 PR**：检测到问题后，直接生成可合并的 PR/补丁，而不是只给一份报告。对非技术用户，提供"一键应用"按钮。

3. **"上线徽章"**：扫描通过后生成一个可嵌入网站页脚、也可导出为 PDF 的证明，包含扫描时间、覆盖项、修复记录。这是给企业客户和投资人看的东西。

4. **持续监控**：接一个 GitHub App 或定时任务，每次部署后自动重扫。因为 AI 生成的应用迭代极快，一次扫描没有意义。

**技术实现**

- **检测层**：不需要重型静态分析。核心是三条腿——(a) 对 Supabase/Firebase 的配置 API 做只读探测；(b) 从公开 URL 做黑盒探测（尝试匿名读写、检查存储桶列表权限）；(c) 对前端产物做正则 + AST 的密钥扫描。
- **修复层**：把常见问题做成模板化的 patch（比如"为 X 表生成 RLS policy"），用 LLM 做适配而非从零生成——LLM 在这里只负责"把这个模板套到你的 schema 上"，不做自由发挥。
- **验证层**：修完之后重跑一遍探测，用实际行为验证而不是"看代码觉得修好了"。这一步是整个产品的信任基础。

**MVP 范围（4 周）**

- 只支持 Supabase 一个平台（用户量最大、问题最集中、API 最友好）
- 只做前三类检测 + 一份 PDF 报告
- 不做自动修复，先验证"检测准确率"和"用户是否愿意付费"
- 形态：一个网页，输入域名或粘贴 Supabase 项目 URL，60 秒出结果

**定价策略**

- **免费**：单次扫描，只显示"有/无高危问题"和数量，不显示详情（制造付费动机）
- **Starter 29 美元/月**：完整报告 + 每月 5 次扫描 + 修复指南
- **Pro 99 美元/月**：自动修复 PR + 每次部署自动重扫 + 上线徽章

### 创意三：FormProof —— Agent 替人提交正式表单的"证据链"

**产品定位**

一句话：**让 Agent 不只是"帮你填表"，而是"填完之后，你能证明它对"。**

不做一个更好的表单填写工具（那是一堆浏览器插件在抢的红海），只做"填写过程中的留痕 + 与权威规则的逐条比对 + 可回放的执行录像"。定位是"Agent 进入法律流程的门票"。

切入口选**个人报税**——IRS 已经开源了 Direct File 的规则与校验逻辑，这是史上第一次有国家级表单系统的校验规则是公开代码。

**核心功能**

1. **可回放执行记录**：Agent 的每一次读表、填值、跳转、校验，都记录成一条带时间戳的事件。事后可以像看录像一样回放："第 3 页第 2 栏，我在 14:22:07 填了 12345，依据是你上传的 W-2 第 1 栏。"

2. **逐条规则比对**：把官方校验逻辑（如 Direct File 的 schema 与 rule 定义）跑一遍，输出"通过 X 项 / 警告 Y 项 / 失败 Z 项"，每个失败项直接定位到字段。

3. **来源溯源**：每个填进去的值都要绑定来源（哪份文件、哪一页、哪个字段）。没有来源的值标红——这是防止 LLM 幻觉最有效的手段。

4. **变更 diff 与确认**：用户修改任何字段，生成 diff，并提示该修改是否会影响其他字段的联动（税法里到处都是这种联动）。

5. **导出两份东西**：一份是给税务局的表单，一份是给用户自己的"填写证据包"（含所有来源、所有决策、所有校验结果），用于日后审计或申诉。

**技术实现**

- **执行层**：浏览器 Agent（Playwright/CDP）做实际操作，但所有动作经过一层"录制代理"，每个动作产生结构化事件。这层代理是整个产品的核心资产。
- **规则层**：把官方开源规则解析成可执行的校验器。IRS Direct File 的代码是 TypeScript，可以直接跑；其他国家/场景（签证、补贴）需要自己写规则，这是长期投入。
- **溯源层**：文档解析（PDF/图片 → 结构化字段）时保留坐标信息，填表时把"目标字段"和"来源坐标"绑定。
- **模型角色**：LLM 只负责"这段话对应哪个字段"的语义映射，不负责数值计算，也不负责最终决定。所有数值都从来源文档原样搬运，可核对。

**MVP 范围（8 周）**

- 只做一个场景：美国个人联邦报税（1040），只支持 W-2 收入 + 标准扣除
- 只做三件事：填表、规则校验、导出证据包
- 不做提交（用户自己去官方系统提交），先把"填得对"这件事做到极致
- 目标：100 个真实用户跑完，人工复核准确率 > 98%

**定价策略**

- **免费试用**：完整填一遍，看校验结果，不导出
- **成功费 39 美元/次**：导出完整表单 + 证据包。按结果付费，用户心智负担最低
- **Pro 99 美元/年**：含全年变更提醒、二次申报、州税
- **B 端授权**：把"可审计执行层"授权给会计师事务所和代办机构，按席位收费——这是规模化收入的来源

需要说清楚的风险：**这是一个强监管、强责任的品类。** 产品必须明确"不提供税务建议"，并且在 MVP 阶段坚决不做自动提交。证据链的价值恰恰在于：**它让"不自动提交"这件事不再是一个妥协，而是一个卖点。**

四件事的共同结构是：**供给侧的爆炸式增长，必然带来验证侧的严重短缺。** 而验证侧恰恰是过去被"专业门槛"保护着的领域——因为有门槛，所以稀缺性被掩盖了；门槛一旦消失，稀缺性立刻暴露。

这个规律在历史上重复过很多次：博客平台普及之后，稀缺的是搜索引擎；电商平台普及之后，稀缺的是评价体系和支付担保；短视频普及之后，稀缺的是内容审核。**每一次"人人可生产"，都会催生一个"人人需要验证"的新市场。**

今天 AI 正好走到了这个位置。

### 三个值得警惕的地方

1. **"安全扫描"这个品类容易被平台方吞掉。** Supabase、Vercel 完全有能力在自己的控制台里加一个"安全检查"按钮。VibeGuard 的护城河不能是"检测能力"，必须是"跨平台 + 上线徽章 + 保险/合规背书"这些平台方不愿意做的东西。

3. **可审计执行层的监管风险被严重低估。** 一旦产品真的介入报税、签证这类流程，就会撞上"无照提供专业服务"的红线。合规路径要提前想清楚：要么做成"工具"（用户自己操作），要么和有牌照的机构合作。
