## 📊 今日核心洞察

### 热点话题

1. **Dharma AI 把"分词器"从一个默认设置，变成了 77% 的成本杠杆**：这篇 Hugging Face 博客讲的事，粗暴地说就是——**你的模型是垂类的，但你的词表还是通才的**。他们在生产里跑一个葡萄牙语作文评分器，基座是 Qwen3-4B，已经做过任务微调，模型只有 4B，看起来已经很省了。但他们发现两处浪费同时存在：一是**碎片化**——评分器每次输出都以同一段 JSON 外壳、同一批能力项名称、同一套评语开头，而这些最高频的字符串被切成了很多 token；二是**冗余**——词表里 151,669 个条目，其中几万个这个任务几乎永远用不到，但模型每生成一个 token 都要为全部条目算一遍概率。他们用 VocabX 重造词表，**基座没换、数据没换、训练配方没换**，实测推理成本降了 77%。这件事的产品含义被严重低估了：所有人都在卷模型、卷量化、卷蒸馏，**而词表是成本结构里最靠前、最没人碰的那一层**。

2. **Allen AI 的 LitPivot 想解决的，是研究者"读不完所以想不出"的问题**：它不是又一个"文献摘要器"。摘要器解决的是"这篇讲了什么"，而 LitPivot 解决的是"**在我的题目周围，还有哪片空地**"。做法是把研究想法放进文献景观里做**动态情境化**——随着你读的东西变化，系统重新计算你的想法相对于现有工作的位置：哪里已经被做透了、哪里是矛盾的、哪里的方法可以搬过来。这个方向的聪明之处在于它承认了一件事：**科研里最贵的一步不是执行，是选题**。选题错了，后面全是沉没成本。而今天的 AI 工具几乎全在加速执行（写代码、跑实验、画图），几乎没人认真做"选题"这一段。

3. **NVIDIA 的 Kumo Relational 在说一件很刺耳的话：关系型数据上，你可能不需要训练**：企业里 80% 的结构化数据躺在关系库里——用户表、订单表、事件表、日志表，靠外键连成一张巨大的图。过去要在上面做预测（这个客户会不会流失、这笔订单会不会退、这台设备什么时候坏），标准路径是特征工程 + 训练。Kumo 的路子是**直接在关系图上做零样本推理**，不用为每个任务训一个模型。如果这条路在真实数据上站得住，它动摇的是整个"企业 AI 项目"的成本模型：**从"一个任务一个模型、三个月一个项目"，变成"接上库、问问题、出预测"**。它也解释了为什么 2026 年企业 AI 的采购重心在从"模型"往"数据接入层"移。

4. **HN 上的 Corgi 暴露了一个真实的管理问题：一个人已经在同时开五个 Agent 了**：这个 Show HN 的作者做了个 agent multiplexer——把 Codex、Claude Code、Pi 的多个会话放在一个界面里，显示每个 Agent 在干什么、有活动流、F1 跳到下一个未读、按 workspace 统计 CPU/内存/GPU 占用、还能用便宜模型帮你总结"这个 worktree 是干嘛的"。这条帖子只拿到了几十个点，但它描述的是**当下很多工程师的真实工位**：三个终端窗口、四个 Agent、五个 worktree，人变成了调度器。**当 Agent 数量超过 3，瓶颈就不再是模型能力，而是人脑的上下文切换**。这是一个明确的产品缺口，而且今天几乎没有像样的商业产品在做。

5. **Google 开始付钱让用户少用电，好让自己的数据中心多用点**：这条新闻表面是能源新闻，实际是 AI 经济学的一个路标。当训练和推理的用电需求开始和居民用电抢同一张电网，**电力变成了算力的前置约束**，而不再只是运营成本。Google 的做法是需求侧响应：高峰期付钱请你关空调，把容量让给数据中心。这套机制在电力行业很成熟，但**把它和 AI 工作负载调度连起来的产品还不存在**——什么时候该把大批推理任务挪到电价低谷、哪个区域的哪块 GPU 现在最"绿"也最便宜，这是一道纯粹的运筹题，而且省下来的都是净利。

### 技术趋势

1. **成本工程正在从"模型内"走到"模型外"**：量化、蒸馏、MoE 是模型内的省法，已经卷到边际收益递减。VocabX 提醒大家，**词表、tokenizer、输出格式、JSON 外壳、prompt 结构**这些"模型外"的东西，往往有十倍的改进空间却没人碰。一个可复用的判断：**任何在你系统里高频重复出现的字符串，都应该被当成一个成本项来设计**——不管是 schema、话术模板，还是工具调用的参数名。

2. **AI 工具的价值正在从"执行"往"判断"上移**：LitPivot 做选题，ThinkingBox 做验收，Corgi 做调度，三个东西在不同的层，但都在做同一件事——**替人做"接下来该干什么"的判断**。执行层（写代码、生成文案、跑 SQL）已经高度商品化，价格战打得血流成河。判断层还是一片空地，而且它天然更难被替代，因为它需要领域知识和上下文积累。

3. **"零样本"正在重新定义企业 AI 的交付周期**：Kumo 的关系型零样本、OlmoEarth 的预计算嵌入（昨天的日报聊过）、AnyLanguageModel 的端侧模型，共同指向一个模式——**把"为每个任务训练"换成"接上就能用"**。对产品团队的直接启示是：如果你的 AI 产品第一句话是"我们需要先收集一批标注数据"，那你的销售周期就已经输了。**先交付一个不完美但立刻能用的结果，再谈微调**。

4. **Agent 的竞争维度从"能力"转向"可管理性"**：Corgi 这类工具的出现是一个信号。当 Agent 能干活之后，客户的问题立刻变成：**我怎么知道它现在在干嘛？它花了多少钱？它卡在哪了？同时开十个我怎么管？** 这和 2010 年代从"单机软件"到"集群管理"的演进一模一样。Agent 可观测性、成本归因、会话编排，会成为独立品类。

5. **算力、电力、碳排正在合成一个新的调度问题**：Google 的需求侧响应只是一个信号。当推理成本里电费占比上升，**"在哪跑、什么时候跑、用什么卡跑"** 就有了实时的套利空间。这个方向的赢家不会是大模型公司，而是**做调度中间层的人**——它不需要模型能力，只需要价格信号和一点运筹学。

## 🎯 潜在需求分析

### 需求 1：垂类 AI 产品毛利被"看不见的那一层"吃掉

**痛点来源**：
- 2026 年做垂直 AI 的团队，几乎都用同一条路径：拿 Qwen / Gemma / Llama 开源基座，做 SFT，部署，卖订阅或按调用计费。**所有人都在同一个成本起跑线上，也都在同一堵墙上**：模型已经量化到 4bit、batch 已经调满、能省的都省了，毛利还是被推理成本压得死死的
- 被忽略的是**进入模型之前**的那一层。一个做合同审查的产品，输出永远是同一套 JSON：`{"clause_type": ..., "risk_level": ..., "suggestion": ...}`，同样几个字段名每天重复几十万次；一个做医疗编码的产品，输出永远是那几千个 ICD 编码。**这些高频固定字符串在通用词表里被切得稀碎**，每个都多花两三倍 token
- 更贵的是冗余词表：151,669 个条目，你的垂类场景可能只用到 8,000 个。但**每生成一个 token，softmax 都要为全部 15 万个条目算分**。在小模型上，这一层开销占比高得惊人——模型越小，词表开销占比越大，这是个反直觉但很硬的数学事实
- 现实是：**没有团队会专门为这件事配一个人**。重训 tokenizer 需要动 embedding 层、要重新对齐、要验证不降低下游指标，属于"知道有价值但排不上期"的活。于是所有人都在为一层可以省 50-77% 的成本持续付费

**具体场景**：
一家做跨境电商合规文案的团队，用 7B 模型生成各国站点的商品合规描述，每天 200 万次调用。他们的账单里，模型推理占 62%，而他们卖的是 $99/月 的 SaaS。CEO 算过账：如果推理成本降一半，毛利率从 41% 到 58%，公司立刻从"需要融资"变成"可以自己活"。他们试过换更小的模型，效果掉得厉害；试过自己做量化，已经做过了。**他们不知道的是，他们输出的那套固定 schema 和那 400 条合规话术，占了输出 token 的六成**。如果把这套东西压成单 token，再砍掉用不到的 14 万词表条目，账单能砍掉一半以上，而模型效果几乎不动。

**市场机会**：
- 目标客户：所有做垂直 SLM/小模型产品的团队（法律、医疗、金融、电商、教育、客服），尤其是**按 token 计费或按次计费、毛利敏感**的
- 产品形态：**TokenFit —— 垂类模型的词表与推理成本优化平台**
  - **语料扫描器**：接入你的生产日志/prompt 模板/输出样本，统计真实的 token 分布，输出"你的成本花在哪 100 个字符串上"的可视化报告（这一步本身就能卖钱，因为它常常直接暴露出 30% 的浪费）
  - **词表重造**：按 **token 成本而非词频** 重新构建词表（VocabX 的核心洞察），保留基座能力所需的最小通用集，为高频 schema/话术/领域术语分配专用 token
  - **embedding 对齐**：自动完成新词表下的 embedding 初始化与短程继续预训练，保证下游指标不退化；内置"退化检测"对比原始模型
  - **一键产出**：导出可直接部署的模型权重 + tokenizer + vLLM/TensorRT-LLM 配置
  - **成本仪表盘**：上线后对比"优化前 vs 优化后"的每千次调用成本、P99 延迟、任务准确率
- 定价：诊断报告 $2,000 一次性（可抵扣）；优化交付 $15k-40k/项目 或 按节省成本的 20% 分成（首年）；SaaS 版 $800/月 持续监控 token 漂移
- 壁垒：**这套活的技术门槛不在"重训 tokenizer"（开源工具能做），而在"重训之后不掉点"的工程配方和验证方法论**。谁先把"降本不降质"做成可复现的流水线，谁就拿到定价权
- 风险：客户会想"我们自己也能做"。对冲方式是**把交付做成服务而非软件**——他们能拿到代码，但拿不到那套验证配方和踩过的坑

### 需求 2：研究者和小团队"选题"这一步，今天完全靠运气

**痛点来源**：
- 科研和产品创新的瓶颈早就不是"跑不动实验"，而是**不知道该跑哪个实验**。一个博士生开题，要在自己方向的两三百篇近三年论文里，判断"哪个点还没人做、哪个点做了但做错了、哪个点的方法可以搬过来"
- 今天的工具全在错误的一端：Zotero 管引用、Semantic Scholar 做相似检索、ChatGPT 做单篇摘要。**没有一个工具回答"我的想法在这个领域的版图上处于什么位置"**
- 更痛的是**动态性**：你上周读的东西，这周就多了一篇高度相关的新论文。人的记忆是静态的，文献是流动的，**位置判断很快过期**
- 后果很具体：大量论文在重复已有的工作（只是换了个数据集），大量创业公司在做已经被验证过不成立的方向。**信息不对称造成的浪费，比算力浪费大得多**

**具体场景**：
一个三人小团队想做"用 LLM 做数据库查询优化"的产品。他们有直觉：LLM 不擅长精确的代价估算，但擅长理解查询意图。问题是——这个方向 2023 年以来至少有两百篇论文，其中至少三十篇做过"LLM 生成 hint"，有些失败了，失败原因写在论文第七页的一个表格里，没人会读到。**他们需要的是一个系统，能告诉他们：哪些子问题已经死了、为什么死的、哪条路还有缝**。今天他们只能靠一个人读两周论文，然后凭感觉下注。

**市场机会**：
- 目标客户：高校课题组、企业研究院、做 0-1 的创业团队、VC 的技术尽调团队（这个群体付费能力最强且最被忽视）
- 产品形态：**LitPilot —— 研究选题的情境化导航器**
  - **想法录入**：用自然语言写一段你的想法（不必成形），系统抽取其中的"问题-方法-场景"三元组
  - **景观定位**：把想法映射到文献景观上，输出三类结果——**已被占据**（谁做的、做到什么程度）、**相邻可迁移**（别的方法在这个问题上还没试过）、**矛盾区**（两篇结论冲突，说明这里有争议，争议就是机会）
  - **失败挖掘**：专门抽取论文里的 limitation / negative result / future work 段落，建成"这个领域死过哪些路"的知识库。**这是最稀缺、最没人整理的数据**
  - **动态追踪**：订阅你的选题，每天新论文进来时重新计算位置，一旦有人做了你想做的事，立刻告警
  - **可执行输出**：不是给一堆引用，而是给"三个可以在两周内验证的最小实验"
- 定价：个人版 $29/月；课题组版 $199/月（5 人）；企业研究院 $2k/月（含私有文献库接入与自定义领域）
- 壁垒：**"失败知识库"的积累**。论文的 abstract 谁都能抓，但"这篇其实没成功、原因是 X"需要深读和结构化，一旦积累成库，就是别人抄不走的资产
- 风险：LLM 幻觉在学术场景是致命的。**每一条结论必须能点回原文的具体段落**，宁可少给结论也不能编

### 需求 3：一个人管五个 Agent，缺的不是更强的模型，是一个"值班台"

**痛点来源**：
- 重度使用 coding agent 的工程师，今天的工作状态是：三个终端、四个 Agent、五个 worktree 并行。**人从"写代码的"变成了"分派任务和验收结果的"**
- 但这套流程完全靠人肉维持：哪个 Agent 卡住了、哪个在等输入、哪个跑完了、哪个烧了 40 美元还在原地打转——**全靠切窗口看**
- 切换成本被严重低估。一次上下文重建平均要 40 秒到 2 分钟（读 diff、回忆任务、判断进度），**一天切五十次，就是两个小时纯损耗**，而且是最消耗意志力的那两个小时
- 现有工具解决不了：IDE 是围绕"一个项目一个窗口"设计的，终端复用器（tmux）只管进程不管语义，Agent 厂商自己的 UI 只管自己家的 Agent。**没有人做跨厂商的那一层**

**具体场景**：
一个独立开发者同时推进三个项目：给客户 A 修一个 bug（Claude Code 在跑）、给产品 B 加一个功能（Codex 在跑）、在读一篇论文准备写 demo（Gemini CLI 在跑）。他去泡杯咖啡，回来看到六个窗口，其中两个在等他确认权限、一个报错退出、一个已经改完了三个文件但他不知道改得对不对。**他真正想要的是一块屏幕：谁在等我、谁在干活、谁干完了、谁干砸了、今天花了多少钱**，点一下就能跳进去，按一下就能让它继续。

**市场机会**：
- 目标客户：重度 Agent 用户（独立开发者、AI native 小团队）、以及**企业内部开始批量部署 coding agent 的工程团队**（后者才是钱多的地方）
- 产品形态：**FleetDeck —— 跨厂商 Agent 值班台**
  - **统一接入层**：把 Claude Code / Codex / Gemini CLI / 自建 Agent 统一成一个"工位"抽象，共享会话列表、resume、账号切换
  - **状态机视图**：每个 Agent 一个卡片，明确四态——**运行中 / 等待输入 / 已完成待验收 / 失败**。等待输入和待验收要主动推送到手机
  - **活动流摘要**：用便宜的小模型把每个 Agent 最近 20 步压成三行话（"在改 auth 中间件，已经改了 4 个文件，测试没跑"），而不是让人读原始日志
  - **成本归因**：按 workspace / 项目 / Agent 统计 token 与美元，支持预算上限与自动熔断
  - **验收队列**：所有"已完成"进入一个队列，逐个看 diff、一键 accept / 打回重做
  - **团队版**：多人共享一支 Agent 舰队，能看到"谁占了哪台机器、哪个任务在谁手上"
- 定价：个人版 $19/月；团队版 $25/seat/月（含共享舰队与审计日志）；企业版私有部署 $20k/年起
- 壁垒：**接入层的广度与稳定性**。这件事没有技术护城河，但有"支持了第 12 个 Agent"的苦活护城河，而且一旦成为团队默认工位，迁移成本很高
- 风险：**Agent 厂商可能自己做**（Claude Code 已经在做多会话）。对冲是坚持跨厂商中立——**用户越是混用多家，你越有价值**

### 需求 4：AI 工作负载的电费，没人当成一个可优化的变量

**痛点来源**：
- 推理成本的构成在变。过去大家只盯 GPU 小时单价，现在**电费在总成本中的占比越来越高**，尤其是在自建集群和中型 AI 公司里
- 电价不是常数：分时电价、区域差价、绿电配额、需量电费，**同一次推理在不同时间不同地点跑，成本能差 3-5 倍**
- 但今天的调度器（K8s、Ray、各家推理平台）**只看 GPU 利用率，不看电价**。它们会把任务塞进最空的机器，而不是最便宜的时刻
- Google 开始付钱让居民让电，说明供需已经紧张到要用价格手段调节。**这个信号对小公司是利好**：你不需要建电厂，你只需要在对的时间跑
- 更隐蔽的一层：越来越多的企业有"碳排披露"义务（尤其出口欧洲的），**"这次训练排了多少碳"正在从 ESG 报告里的一行字，变成采购问卷里的一个问题**

**具体场景**：
