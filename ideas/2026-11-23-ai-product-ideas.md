## 📊 今日核心洞察

### 一句话：软件的"分发单位"正在从 App 变成 Skill，而治理层几乎没人做

今天的 GitHub Trending 是一张非常罕见的图——**前十名里有七个是 Agent Skills / Agent 原生工具，而不是应用**：

- **Claude-BugHunter**（17,687 stars，单日 +1,721）：82 个技能、681 份已披露漏洞报告模式，专做漏洞挖掘与红队。
- **superpowers**（obra）：一套"能用的"智能体技能框架 + 软件开发方法论。
- **CLI-Anything**（HKUDS）："让所有软件都变成 Agent 原生"——把任意 GUI/API 包装成 CLI 供 Agent 调用。
- **app-store-compliance**（单日 +617）：124 条应用商店拒审模式 + **112 个正在逼近的合规截止日**（EU AI Act、DSA、COPPA、年龄法规），并且直接做成给编码 Agent 用的 skill。
- **stitch-skills**（Google Labs，11,896 stars）：官方 Agent Skills 库，遵循 Agent Skills 开放标准。
- **cursor/plugins**（18,419 stars）：Cursor 的插件规范与官方插件。
- **last30days-skill**：跨 Reddit / X / YouTube / HN / Polymarket 做研究的技能。

这个结构变化值得停下来看清楚：**过去两年，"AI 应用"的分发单位是网站和 App；现在，分发单位变成了一个 markdown 文件 + 几个脚本，挂在某个 Agent 宿主上。** 一个 17k star 的 skill 包，不需要服务器、不需要 UI、不需要 App Store 审核，就能触达几十万开发者——这是十年来最低的软件分发成本。

但随之而来的是一个巨大的空洞：**skill 没有 SBOM、没有签名、没有权限声明、没有版本审计、没有回滚。** 你 `git clone` 一个 82 技能的包，它就能读你的 `~/.ssh`、跑 `curl`、改你的 CI 配置。它今天有 17,687 个 star，其中 1,721 个是今天点的——**没有一个人读过它的全部 82 个技能**。

这不是"安全隐患"这种说法层面的问题，这是一个**采购问题**：企业想让团队用这些技能提效，安全和法务的第一个问题就是"这个包是谁写的、改过什么、能碰什么"。今天没人能回答。

### 第二条线：arXiv 今天在集体研究"Agent 出事之后怎么办"

随便扫一眼今天 cs.AI 的新论文，会发现一个非常集中的主题簇：

- **ROGUE-AI**：Agentic Security Events 的复现、审计与调查。
- **Backtracking Agent Applications Security Incidents**：Agent 出事后如何回溯定位 CEP（compromise entry point），复盘哪些记忆/工具调用被污染。
- **SoK: LLM Capability in Software Vulnerability Research**：系统化梳理 LLM 在漏洞发现、验证、修补上的真实能力边界。
- **Verify the Verifier**：UVM 验证平台"通过了测试"不等于"符合规格"——需要在规格层面做交叉检查。
- **Realized versus Population Reliability**：把 self-consistency 做成 anytime-valid 的可靠性认证，而不是跑完 N 次看多数。
- **GEOHunter**：在野外测绘生成式引擎优化（GEO）推广网络——**已经存在成规模的黑产，专门操纵生成式答案里的品牌露出**。

把这几篇的标题连起来读，其实是一句话的六个侧面：

> **Agent 已经在真实世界里删文件、发钱、改代码、影响舆论了，而我们既没有黑匣子，也没有事故调查方法，更没有"这个答案是被操纵过的"的检测手段。**

学术界在补方法论，工业界一个产品都没有。这个 gap 就是今天的机会。

### 第三条线：本地推理的成本曲线又下了一级台阶

Hugging Face 这周几条更新串起来看很有信息量：

- **Inkling 2 Mini**：前沿性能压到本地可跑的尺寸，社区已经有人在 **5.4GB 内存**里跑起来（HN 292 分）。
- **180B 参数、32GB 内存**：MoE expert streaming 把超大模型的推理内存需求打下来一个数量级。
- **minimind**：两小时从零训一个 64M 模型，Trending 常客。
- **llama.cpp v1.0.0**：本地推理底座终于有了稳定版语义。
- **BotPsy / Rumble-2-Flash**：亚十亿参数的端侧 agent 与 0.5B 多语语音。

含义很直接：**"每个开发者本机跑一个能干活的 Agent"从奢侈品变成默认配置。** 而本机 Agent 能读本地文件、能连内网、能跑 shell——**它的攻击面比云端 Agent 大得多，但监控能力几乎为零。** 这和第一条线（skill 无治理）、第二条线（无取证）是同一个洞的三个入口。

### 所以今天的判断是

**AI 产品的竞争焦点，正从"能力"转向"边界"。**

- 能力层已经过度供给：生成、写码、找漏洞、做研究，全都有 17k star 的开源包免费给你。
- 边界层完全空白：这个技能能碰什么？这次调用为什么发生？这个答案有没有被人操纵？这个 Agent 出事之后能不能复盘到具体一步？

能力免费、边界收费——这是软件史上反复出现的利润迁移路径（开源数据库 → 托管与审计；开源容器 → 镜像扫描与运行时防护；开源 LLM → 网关与可观测性）。**Agent 生态现在正好走到"开源已经赢了，治理还没开始"的那个点。**

## 🔍 潜在需求分析

### 需求一：企业需要 Agent Skill 的"供应链安全"，而不是又一份渗透测试报告

**痛点来源**

企业引入 Agent 技能包的路径，今天基本是这样的：某个工程师在 Trending 上看到一个 17k star 的包，`git clone` 到本地，`cp -r` 进 `.claude/skills/`，跑通了，写进团队 wiki，三个月后全组都在用。

这条路径上有四个没人管的环节：

1. **来源不可信**：包的作者是谁？有没有关联账号刷 star？上个版本和这个版本 diff 了什么？
2. **权限不可见**：这个 skill 会读哪些路径、发哪些网络请求、调用哪些 CLI？没有任何声明格式强制它写出来。
3. **行为会漂移**：skill 依赖的模型、CLI 版本、外部 API 一变，行为就变。没有基线，就没有"它以前是这样"这种说法。
4. **无法回滚到"已知安全版本"**：因为从来没有"已知安全版本"这个概念。

对比一下传统依赖治理的成熟度：npm 有 lockfile、有 `npm audit`、有 SCA 扫描、有私有 registry、有 provenance attestation（SLSA）。**Agent skill 生态这五样一样都没有，但它的权限比一个 npm 包大得多**——npm 包最多在构建时跑个 postinstall，skill 是在你的 shell 里、以你的身份、读你的文件。

**具体场景**

- 一家金融科技公司的平台团队，被安全部门要求"盘点所有在用的 AI 技能包并给出风险评估"。他们打开各人的 `~/.claude/skills/`，发现 47 个来源不明的目录，其中 12 个包含网络请求，3 个包含 `rm -rf` 或等价的清理逻辑。**没有人能说出这 3 个是干什么用的。**
- 一家 SaaS 公司的 DevEx 团队想在公司内推广 skill 复用，但法务要求"任何进入生产工具链的第三方代码必须有明确许可与责任人"。于是推广停摆——不是不想用，是**没有可审计的引入流程**。
- 一个开源 skill 作者想给自己的包加"可信"标签，但没有任何中立机构能替他背书，只能靠 star 数——而 star 数是可以买的。

**市场机会**

这是一个典型的"合规驱动 + 平台驱动"双引擎市场：

- **合规侧**：EU AI Act 的分阶段义务、SOC2 对"第三方组件"的要求、金融行业的供应商准入，都会把"AI 技能包"纳入既有审计框架。**审计师会问，客户答不上来，就需要工具。**
- **平台侧**：谁能成为"企业内 skill 的登记与分发中心"，谁就掌握了企业 Agent 生态的入口。这个位置比做单个 skill 值钱得多。
- **定价锚点清晰**：可以直接对标 SCA / 软件供应链安全产品（按开发者席位或按扫描仓库数计费），客户已有预算科目，不需要教育市场。

**关键洞察**：这个产品的护城河不在"扫描规则多"，而在**成为标准**——如果 skill 的权限声明格式（类似 `SKILL.md` 的 front-matter 扩展）由你定义并被主流宿主接受，你就自动成为所有 skill 的注册中心。

### 需求二：Agent 出事之后，企业需要"黑匣子"，而不是聊天记录

**痛点来源**

今天 arXiv 上两篇论文（ROGUE-AI、Backtracking Agent Applications Security Incidents）在解决同一个工程问题：**Agent 删了库、发了错款、把客户数据发给外部 API 之后，怎么复盘？**

现有工具给不出答案，因为它们记录的东西不对：

- **日志记录的是"调用"，不是"意图"**。你知道它调了 `delete_file`，但不知道它当时"以为"自己在干什么。
- **上下文是有状态的**。Agent 的决策依赖记忆、检索结果、之前的工具返回值。这些东西在事后是不可重建的——除非你当时就存了。
- **污染会传播**。一次 prompt injection 进入记忆，之后 20 步的行为都是"合理地错的"。要定位 CEP，必须做**因果回溯**，而不是按时间顺序翻日志。
- **责任要落到人**。审计要回答的不是"模型错了"，而是"哪一步应该有人工闸门而没有"。

**具体场景**

- 某公司的编码 Agent 在一个重构任务里删掉了一个"看起来没用"的迁移脚本，两周后生产环境回滚时发现回不去。复盘会上，团队花了三个小时翻聊天记录和 CI 日志，仍然说不清"它是基于什么信息判断这个文件没用的"。
- 一个客服 Agent 被用户在对话里注入了指令，把退款额度提高了 10 倍。事后安全团队想知道：这个注入是从哪条消息进来的？中间经过了哪些工具？有没有第二笔同类操作？**现有日志只能给出一个时间线，给不出因果链。**
- 合规审计要求提供"过去 90 天所有涉及资金操作的 Agent 决策及其人工审批记录"。团队发现这些信息散落在四个系统里，且没有一个能证明"未被篡改"。

**市场机会**

这个品类可以对标两个成熟市场，取两者的交集：

- **可观测性（Observability）**：Datadog / LangSmith 那套，按 trace 量计费，客户已经接受"Agent 需要 tracing"。
- **数字取证与事件响应（DFIR）**：客单价极高、合规刚需、采购周期短（出过事就有预算）。

差异化的点在于**"可回放"而不是"可查看"**。查看是给人看的仪表盘；回放是给机器重跑的能力——把当时的上下文、工具返回、模型版本固定下来，能在沙箱里逐步重演。**这是"证据"和"日志"的区别，也是能不能上法庭的区别。**

**关键洞察**：卖点不是"防止出事"，而是"出事之后 10 分钟内说清楚"。前者客户觉得你在卖保险，后者客户觉得你在卖消防车——**消防车更好卖，因为火已经在烧了。**

### 需求三：品牌方需要"生成式答案里的可见性"，而且需要一个能识破灰产的版本

**痛点来源**

GEOHunter 这篇论文的价值不在于它发现了灰产，而在于它证明了**这个灰产已经成规模、成网络、可测绘**：一批推广站点互相引用、专门针对生成式引擎的检索与合成机制做优化，把特定品牌塞进 AI 的回答里。

与此同时，HN 上 424 分的《Perplexity and Intelligence》在讨论另一面：**当搜索变成"AI 直接给答案"，被引用的来源就成了唯一的流量入口。** 没被引用 = 不存在。

品牌方现在的处境极其被动：

- 传统 SEO 工具测的是"关键词排名第几"，生成式答案是**一段合成的文字**，没有排名这个概念。
- 品牌方不知道自己在不同模型、不同提问方式下被怎么描述——**说错了也没有告警**。
- 竞品可能正在用灰产网络系统性地污染这个描述，而品牌方连检测手段都没有。
- 一旦被写进答案的负面描述形成，纠偏周期以月计，且没有"申诉入口"。

**具体场景**

- 一家消费品牌的增长团队发现，问某个 AI 助手"XX 品类哪个牌子好"，自己的品牌连续三周没出现，而一个知名度更低的竞品稳定出现在前三。他们怀疑被做了 GEO，但无法证明，也不知道该改什么。
- 一家 B2B SaaS 公司发现 AI 助手在回答"XX 工具的价格"时给出的是两年前的定价，导致销售线索质量下降。**没有任何工具能告诉他们"这个错误描述在多少个提问变体下出现"。**
- 一家医疗健康公司被 AI 回答里的错误适应症描述困扰，法务要求"持续监测并留证"，但现有舆情工具完全覆盖不到生成式答案。

**市场机会**

三层价值，越往下越值钱：

1. **监测层**（好卖、低门槛）：跨模型、跨提问变体的品牌描述快照 + 变更告警。对标 SEO 监测工具定价。
2. **诊断层**（中价）：为什么没被引用？是检索没抓到、还是抓到了但合成时被忽略？给出可执行的修复建议（结构化数据、权威引用、内容形态）。
3. **反操纵层**（高价、稀缺）：识别针对你的品牌的灰产推广网络，输出证据包。**这一层几乎没有竞品，因为它需要论文级的方法 + 工程化的爬取能力。**

**关键洞察**：不要把它做成"AI 版 SEO 工具"。SEO 工具的客户心智是"提升排名"，GEO 工具的客户心智应该是"**确保 AI 说的关于我的话是对的**"——后者是品牌风险，预算来自 PR / 法务 / 品牌，而不是市场投放，**预算池更大且更抗周期**。

### 需求四：合规截止日在逼近，但没人把它翻译成工程任务

**痛点来源**

Trending 上那个 `app-store-compliance` 项目之所以一天涨 617 star，是因为它做了一件非常务实的事：**把 112 个监管截止日做成了一张可执行的检查表，并且直接交给编码 Agent 去执行。**

这暴露了一个被严重低估的需求：EU AI Act、DSA、COPPA、各州年龄验证法、应用商店审核规则——**这些文本是给律师看的，但执行是工程师的事。** 中间的翻译层几乎是空的。

- 法务给工程一份 40 页的合规备忘录，工程看完只知道"要做点什么"。
- 工程按自己理解打了几个补丁，法务无法验证"是否覆盖了第 12 条第 3 款"。
- 监管更新了指引，没人知道现有实现是否还合规。

**具体场景**

- 一个小团队要在欧盟上线带推荐功能的产品，需要判断自己属于"高风险"还是"有限风险"，以及对应义务。他们请不起外部律所做完整评估，只能靠博客文章猜。
- 一个已上线的 App 收到商店的拒审通知，理由是"未提供 AI 生成内容的标识"。团队改了一版，又被拒，理由是"用户举报机制不完整"。**每次拒审 = 两周收入损失。**
- 一家公司的 AI 功能要过内部合规评审，需要产出"技术措施 ↔ 法条"的映射表。这张表现在靠人手工做，一份要两周。

**市场机会**

这个方向的商业模式很清晰：**把"合规文本 → 工程任务 → 验证证据"做成一条流水线。**

- 输入：产品描述 + 目标市场 + 数据处理方式。
- 输出：适用的法条清单、每条的工程实现建议、可自动验证的检查项（配置检查、UI 检查、日志检查）、以及一份可直接给审计看的映射表。
- 持续价值：法规更新时自动 diff，告诉你"新增了哪三条义务，你的哪些实现受影响"。

**关键洞察**：这个产品最好的形态不是 SaaS 后台，而是**一个能被 Agent 调用的 skill + 一个持续更新的规则库**。客户不需要登录你的网站，客户需要在自己的 CI 里跑一条命令。

## 💡 新产品创意

### 创意一：SkillGuard —— Agent 技能包的供应链治理平台

**产品定位**

> 给企业 Agent 生态做"npm audit + 私有 registry + SBOM"的那一层。
> 一句话：**在你 `git clone` 一个 skill 之前，先让它过一遍我们。**

**核心功能**

1. **静态权限提取（Permission Extraction）**
   不依赖作者声明，直接从代码里推断能力面：读了哪些路径模式、发起了哪些域名请求、执行了哪些二进制、写了哪些环境变量。输出一个结构化的 capability manifest（`read: ~/.ssh/**`, `net: api.github.com`, `exec: git, curl`）。
2. **行为基线（Behavior Baseline）**
   在沙箱里用一组标准 prompt 跑一遍 skill，记录它实际触发了哪些工具、访问了哪些资源。**声明 vs 实际**的差异就是最值得看的地方——一个声称"只读文档"的 skill 实际发起了外网请求，这一条就足够拦下来。
3. **版本漂移告警**
   每次上游更新，自动 diff 权限面和行为面。新增一个 `net:` 域、新增一个 `exec:` 二进制，立刻告警。这是 lockfile 思维的移植。
4. **私有 Registry + 准入流**
   企业内部 skill 登记、责任人绑定、审批记录、版本固定、一键回滚。开发者体验对标 `npm install`：`skillguard add <pkg>` 走私有源，带签名校验。
5. **CI 门禁**
   GitHub Action / pre-commit hook：仓库里出现未登记的 skill 目录，PR 直接红。

**技术实现**

- **解析层**：每个宿主（Claude Code / Cursor / Codex / Gemini CLI）的 skill 格式不同，但实质都是"markdown 指令 + 脚本"。核心是解析 front-matter、抽出引用的脚本文件、对脚本做 AST 分析（Python `ast`、JS 用 tree-sitter），提取文件路径、网络调用、子进程调用。
- **沙箱执行层**：Firecracker microVM 或 gVisor，用 seccomp 限制 syscall，用 eBPF 记录实际文件与网络访问——**eBPF 是关键，因为它是"实际行为"而不是"代码里看起来像什么"的真相来源**。
- **存储层**：capability manifest 用 OCI artifact 存（复用现有 registry 生态，省一大截工程量），签名用 sigstore/cosign。
- **规则引擎**：OPA/Rego 表达企业策略（"禁止任何 skill 访问 `~/.aws`"），策略即代码，可版本化。

**MVP 范围（8 周）**

- 只支持 Claude Code 的 skill 目录格式（覆盖 80% 的现实使用）。
- 只做静态权限提取 + 一个"危险能力"清单（外网请求、shell 执行、敏感路径读写、环境变量读取）。
- 输出一份 PDF/HTML 报告 + 一个 `skillguard scan ./skills` 命令。
- 不做沙箱执行（这是 v2 的活），但报告里明确标注"未验证运行时行为"。
- 目标：让安全团队能在一天内盘完公司所有在用的 skill。

**定价策略**

- **Free**：CLI 单机版，扫 5 个 skill/月，报告带水印。用途是病毒式传播——每个开发者扫完都会把报告转给安全同事。
- **Team $29/开发者/月**：私有 registry、CI 门禁、版本漂移告警、策略即代码。
- **Enterprise $50k+/年**：沙箱行为验证、SSO/SCIM、审计导出、专属规则、供应商准入工作流。
- **关键设计**：免费版必须能产出"让安全团队紧张的报告"，这是从下往上的 PLG 引擎；企业版卖给的是 CISO，不是开发者。

### 创意二：Rewind —— Agent 的飞行记录仪与事故回放台

**产品定位**

> 不是"Agent 可观测性平台"，是"Agent 事故调查工具"。
> 一句话：**出事了，10 分钟内告诉我们它当时看到了什么、以为自己在干什么、哪一步该有人拦。**

**核心功能**

1. **全上下文捕获（Flight Recorder）**
   SDK 级埋点，记录每一步的完整输入：系统提示、检索到的文档原文、工具返回的原始 payload、模型版本与参数、当时的 token 预算。**不是摘要，是原文**——因为复盘时你永远不知道哪一段是关键。
2. **因果链重建（CEP 定位）**
   给定一个"坏结果"（这笔退款错了 / 这个文件被删了），反向搜索所有可能导致它的输入：哪条用户消息、哪份被污染的检索文档、哪次工具返回。用"如果移除这个输入，坏结果是否还发生"做反事实检验——这是论文里 backtracking 思路的工程化。
3. **沙箱重放（Replay）**
   把捕获的上下文固定下来，在隔离环境里逐步重跑。可以单步执行、可以在任意一步注入修改（"如果第 7 步没有返回这个文件列表会怎样"），用于验证事故假设。
4. **闸门审计（Gate Audit）**
   标出所有"按企业策略本该触发人工确认但没触发"的步骤。这是给审计看的核心产出——**它把"模型犯错"翻译成"流程失控"**，后者才是组织能改的东西。
5. **证据包导出**
   时间线 + 因果图 + 原始上下文 + 哈希链，一键导出为可交给监管/客户的证据包。

**技术实现**

- **捕获**：OpenTelemetry GenAI semantic conventions 已经在成型，直接用 OTel 做传输层，避免自建协议。关键是**采样策略**——全量存太贵，只存"涉及写操作/资金/外发"的 trace 全量，其余采样。
- **存储**：对象存储存原文（Parquet + 内容寻址），元数据进 Postgres。成本控制靠分层：7 天热存、90 天温存、之后只留证据包。
- **重放**：确定性重放是难点。做法是**录制所有外部依赖的返回**（模型 API、工具、检索），重放时用录制的响应替代真实调用——这样重放不需要模型确定性，这是工程上唯一可行的路子。
- **因果分析**：先用启发式（时间邻近 + 数据流依赖）生成候选集，再用 LLM 做"这个输入和这个结果有没有因果关系"的判断，最后用反事实重放验证。**三层递进，避免纯 LLM 瞎猜。**
- **防篡改**：每条记录 hash 链式串接，证据包带 Merkle root，可对外证明"未被修改"。

**MVP 范围（10 周）**

- 只支持一个框架（推荐 LangGraph 或自研 Python agent），只覆盖"工具调用 + 检索"两类事件。
- 只做捕获 + 时间线视图 + 单步重放。**不做自动因果分析**（v2）。
- 提供一个"事故复盘模板"：输入坏结果，人工标注可疑步骤，系统做反事实重放验证。
- 目标客户：已经有 Agent 在生产跑、且出过至少一次事故的团队——**这类客户不需要被说服。**

**定价策略**

- **按 trace 量 + 留存期**计费，对标可观测性：$0.30/千条全量 trace（含 7 天留存），90 天留存 $0.8/千条。
- **Incident 包**：$5k/次的事故调查服务（工具 + 我们的工程师帮你跑），**这是最好的获客手段**——出事时没人比价。
- **Enterprise**：$80k+/年，含本地部署、证据包合规认证、闸门策略审计。
- **反常识定价**：对"事故调查服务"不打折、不免费。**免费的事故调查会让客户觉得你不专业，而这是他们最焦虑的时刻。**

### 创意三：AnswerAudit —— 生成式答案的品牌事实核查与反操纵

**产品定位**

> 不是"AI 时代的 SEO 工具"，是"AI 说的关于你的话，是不是真的、是不是被人操纵的"。
> 一句话：**跨模型、跨提问变体，持续监测 AI 如何描述你的品牌，并识别背后的操纵网络。**

**核心功能**

1. **描述快照矩阵（Claim Matrix）**
   把"品牌"拆成一组可核查的断言（价格、适用人群、禁忌、竞品对比、资质），在 N 个模型 × M 个提问变体上采样，抽出模型的实际表述，结构化成一张"断言 × 来源"矩阵。
2. **事实偏差告警**
   与客户提供的权威事实库比对。定价错了、适应症错了、把竞品的功能安到你头上——**任何一条偏差都触发告警，并给出该表述出现的提问分布**。
3. **引用溯源（Citation Graph）**
   抓取答案里引用的来源，构建"哪些页面在塑造关于我的描述"的图。区分权威源、UGC、以及**疑似推广站点**。
4. **灰产网络识别**
   复用 GEOHunter 的思路：找互引聚类、找模板化内容、找注册时间集中/域名相似/内容高度同质的站点群。输出"这个网络在推广谁、覆盖了哪些提问"。
5. **修复建议与验证闭环**
   针对"没被引用"和"被错误描述"分别给建议（结构化数据、权威第三方引用、内容形态调整），改完之后在同一提问集上重测，量化改善。

**技术实现**

- **采样层**：多模型 API + 浏览器自动化兜底（有些生成式答案只在 Web UI 出现）。提问变体用模板 + LLM 扩写，控制在每个品牌 500-2000 条 query。
- **抽取层**：把自由文本答案抽成结构化断言，用 constrained decoding（JSON schema）保证可解析，再做人审校准集。
- **溯源层**：解析引用链接 → 抓正文 → 去重聚类（SimHash + embedding）→ 站点特征提取（whois、模板指纹、外链结构）。
- **图分析**：构建站点引用图，用社区发现找聚类，用"聚类内互引密度 / 对外引用比例"作为操纵信号。
- **成本控制**：这是最大的工程挑战。用分层采样——高频核心问题每日跑，长尾每周跑；用小模型做初筛，只对异常样本跑大模型。

**MVP 范围（6 周）**

- 只支持 2 个模型、1 个行业模板（推荐消费品牌或 B2B SaaS）。
- 只做 Claim Matrix + 偏差告警 + 引用列表。**不做灰产网络识别**（这是 v2 的杀手锏，需要数据积累）。
- 交付形态：每周一份 PDF 报告 + 一个可筛选的 Web 视图。
- 目标：先卖给 5 家被"AI 说错话"困扰过的品牌，用报告换案例。

**定价策略**

- **Starter $499/月**：1 个品牌、2 个模型、500 query/月、周报。
- **Growth $2,000/月**：5 个品牌、全模型、2000 query/月、日更告警、引用溯源。
- **Enterprise $60k+/年**：灰产网络识别、证据包、API 接入、专属行业模板。
- **打包策略**：把"灰产识别"做成单独的 incident 服务（$15k/次），因为它是"怀疑被搞了"的时刻才需要的，价格敏感度最低。

## 🔮 反共识观点

**1. "Agent 可观测性"是个伪品类，"Agent 取证"才是真品类。**

可观测性卖的是"平时看着舒服"，取证卖的是"出事时能救命"。前者是 nice-to-have，预算在工程效率科目；后者是 must-have，预算在风险与合规科目。**同一个技术底座，卖后者客单价高 5 倍、续费率高一倍。**

**2. Skill 的数量会先爆炸再崩塌，赢家是做"减法"的人。**

今天 82 个技能的包、681 份报告模式——这是典型的"能力堆砌期"。半年内会出现"技能太多，Agent 选错技能"的新问题。**下一个爆款不是"更多技能"，而是"给定任务自动裁剪出最小技能集"**——一个技能路由器。这个位置今天空着。

**3. 端侧 Agent 的安全市场比云端大，但没人做。**

5.4GB 内存跑前沿模型意味着"每个开发者本机一个 Agent"。本机 Agent 能读 `~/.ssh`、能连内网、能跑任意 shell——**攻击面比云端大一个数量级，而云端至少有 VPC 和 IAM，本机什么都没有。** 端侧 Agent 的权限沙箱会是一个独立品类。

## 🧩 深挖：为什么是"现在"，而不是半年前或半年后

判断一个产品窗口，最怕的是"方向对但时点错"。上面四个需求都能被论证为"重要"，但重要的东西往往已经在做了。所以需要单独回答一个问题：**为什么今天做，比六个月前做更容易成、比六个月后做更难被抄？**

### 技能生态：从"个人玩具"跨到"团队基础设施"的那条线刚刚被跨过

半年前，Agent skill 还是个人玩家的东西——一个人写几个 prompt 文件，自己用得爽。今天 Trending 上的信号说明它跨线了：

- **出现了"82 个技能 + 15 个 slash command"这种规模的包**。规模一旦到几十个技能，就产生了"我到底装了啥"的管理问题——这是团队需求，不是个人需求。
- **出现了官方背书**：Google Labs 的 `stitch-skills` 明确遵循 Agent Skills 开放标准，Cursor 出了插件规范。**标准出现 = 生态开始收敛 = 治理需求变得可能**（没有标准时，治理工具要为每个宿主重写一遍）。
- **出现了合规驱动的 skill**：`app-store-compliance` 这种"把监管翻成工程任务"的包一天涨 617 star，说明**企业场景已经在用 skill 了**，不只是极客。

跨线的标志是：**使用者的身份从"开发者"变成"开发者的经理和安全团队"**。后者不关心 skill 有多酷，只关心"能不能批"。这就是治理产品的需求起点。

而为什么六个月后做会难？因为**平台方会内置一部分**。Claude Code / Cursor 一定会加"技能权限提示"。但它们只会做"提示"，不会做"企业级准入与审计"——那是 to B 的活，平台方通常留给生态。**窗口在于：在平台只做提示、企业必须做审批的这个空档期，成为事实标准。**

### 取证：从"研究问题"到"采购问题"的转折正在发生

今天 arXiv 上两篇 Agent 安全事件论文（ROGUE-AI、Backtracking）出现在同一个提交日，这个巧合说明研究社区已经把"Agent 事故"当成一个独立问题域了。但学术论文和产品之间通常有 18 个月的鸿沟，这次可能更短，原因有三个：

1. **事故已经在公开发生**。HN 上长期有"Agent 删了我的代码库""Agent 给客户发了错邮件"这类帖子。每一条都是免费的销售线索。
2. **责任归属已经进入法务视野**。当 Agent 代表公司执行操作，"谁负责"这个问题必须有答案。答案需要证据链，证据链需要工具。
3. **技术底座已经就绪**。OTel 的 GenAI 语义约定、内容寻址存储、确定性重放（录制外部依赖返回）——这三样拼起来，工程上已经没有硬障碍。**剩下的只是"有人愿意认真做一遍"。**

六个月后的风险是：**可观测性厂商会向上做**（Datadog 类玩家加一个 "incident replay" 功能），**Agent 框架会向下做**（LangGraph 自带 trace 回放）。所以差异化必须落在**"审计语言"**上——闸门审计、证据包、监管导出，这些是纯工程团队不会做的东西。

### 可见性：GEO 灰产的规模化是先决条件

GEO 这件事有个残酷的前提：**只有当操纵行为规模化到能影响商业结果，品牌方才愿意付钱。** GEOHunter 的贡献在于它证明了"规模化"已经发生——不是个别站点刷存在感，而是成网络的、互相引用的、模板化的推广集群。

同时，《Perplexity and Intelligence》424 分说明另一件事：**用户对"AI 直接给答案"这件事的接受度已经跨过临界点**。当答案成为主要入口，被引用的来源就获得了类似"搜索结果第一位"的经济价值——而所有有经济价值的位置，都会被优化、被操纵、被争夺。

所以时间线是：**入口价值确立（已发生）→ 操纵规模化（已发生，GEOHunter 证明）→ 品牌方感知到损失（正在发生）→ 采购工具（未来 6-12 个月）。** 现在进场，正好赶上"感知到损失"到"形成采购"的那个窗口。

## 🏗 产品化的三个工程难点（以及我的解法倾向）

### 难点一：Skill 的"能力面"没有统一表达

一个 skill 可能包含：一段 markdown 指令、若干 Python/JS 脚本、对 MCP server 的调用、对外部 CLI 的依赖。**四类东西，四种分析方式。**

我的解法倾向是**不追求完备，追求"够吓人"**：第一版只做三类检测——(a) 脚本里的文件路径常量与 `open()`/`Path()` 调用；(b) 网络调用（requests/fetch/curl 字面量 URL）；(c) 子进程调用（`subprocess`/`exec`/`child_process`）。这三类覆盖了 90% 的真实风险，且实现成本极低（正则 + 轻量 AST，甚至不需要完整类型推断）。

**关键产品判断：报告的价值不在于"准确率 99%"，而在于"让安全团队第一次看到全景"。** 一份 80% 准确但覆盖全部 47 个包的报告，比一份 99% 准确但只覆盖 3 个包的报告有用得多。

### 难点二：Agent 重放的确定性

模型输出不确定，工具返回不确定，检索结果不确定——三重不确定，重放几乎不可能。除非**把不确定性全部录下来**。

具体做法：在 SDK 层给每个外部调用打一个 `replay_key`（trace_id + step_index + call_index），录制时存原始响应，重放时按 key 命中录制值直接返回，不真的调用。**这样重放变成"确定性回放一部录好的电影"，而不是"重新演一遍"。**

代价是存储成本，解法是**只对"值得调查"的 trace 做全量录制**：涉及写操作、资金、外部通信、权限变更的，全录；纯读的，只录摘要。这个策略能让存储成本下降一个数量级，同时保住 95% 的调查价值。

### 难点三：生成式答案的采样成本

500 个提问 × 5 个模型 × 每天一次 = 每天 2500 次调用。如果每次都跑大模型，成本直接吃掉毛利。

我的解法是**三层漏斗**：

1. **第一层（每天）**：20 个核心提问 × 2 个主力模型，全量跑。这是"必须知道"的部分。
2. **第二层（每周）**：200 个长尾变体，用小模型或便宜的推理档位跑，只做"是否提及品牌 / 是否出现关键数字"的二值判断。
3. **第三层（按需）**：发现异常时，对相关提问做全模型全变体深挖——**这一层贵，但只在异常时触发，且客户愿意为"深挖"付额外费用。**

成本结构上，第一层占总调用量不到 5%，却提供 80% 的告警价值。这是典型的"用产品设计压成本"，而不是"等技术降价"。

## 💰 商业模式的共同结构：从"工具"到"记录"

这三个产品看起来分散（skill 治理、事故取证、答案核查），但商业结构惊人地相似：

1. **入口是一个免费/低价的自助工具**（CLI 扫描、trace 导出、单品牌监测）。作用是让客户自己发现"问题比想象的多"。
2. **转化点是"第一次事故/第一次审计"**。这三个产品都在等待同一个时刻——客户被问"你怎么证明"。**这个时刻不可预测，但一旦发生，决策周期极短。**
3. **留存靠"记录"**。扫描报告是一次性的，但"历史基线""证据链""变更历史"是累积的。**累积数据 = 迁移成本 = 续费理由。** 这是这类产品最容易被低估的护城河：客户第二年不续费，等于放弃自己一年的证据。

所以产品设计的核心不是"功能多"，而是**"从第一天就开始积累不可替代的历史记录"**。SkillGuard 的版本漂移历史、Rewind 的事故库、AnswerAudit 的描述变更时间线——这三样东西，客户用满一年之后，换供应商的成本高到不可接受。

这也是为什么我在定价上强调"按留存期分层"：**留存期不是成本项，是价值项。** 客户买的是"我能回到一年前的任何一天"，而不是"我能看今天的仪表盘"。
