## 🎯 潜在需求分析

### 需求 1：Agent 一致性/可靠性验证——"上次成功、这次翻车"的生产级焦虑

**痛点来源**：
- **HF 头条敲响警钟**：IBM Research《Your Agent Aced the Task. Will It Do It Again?》明确指出——**Agent 通过一次任务 ≠ 能稳定通过同类任务**；同一 agent、同一任务、仅换随机种子或上下文微扰，成功率可能从 95% 掉到 40%。这是生产环境的"致命不确定"：软件测试领域花了 40 年建立"单元测试-回归测试-CI"体系，而 Agent 时代**没有任何成熟工具回答"这个 Agent 这次行为是否符合预期"**
- **生产试点的惨痛教训**：银行智能客服 Agent 对同一客户问题两次给出不同答案、RPA+LLM 流程周五运行完美周一莫名失败、医疗分诊 Agent 对相似症状给出不同建议——**出一次稳定性事故，试点项目就被打回原型**；企业对"AI 不可预测"的容忍度极低，但 Vendor 只承诺"能力上限"，不承诺"行为下限"
- **模型更新 = 行为漂移盲盒**：供应商每月发新模型版本，企业**不知道新版本在自己的业务场景上是变好还是变坏**——没有"上线前回归"和"上线后基线对比"，只能等事故暴露；HF 的 altk-evolve 系列研究（consistency / memory / routing）说明连大厂自己都还在摸索"如何保证 Agent 稳定"
- **评测与生产的断层**：现有 LLM 评测（benchmark、arena）测的是"单轮问答能力"，而生产 Agent 是**多轮、多工具、多状态的复杂系统**——评测集静态、场景不匹配、评测器本身不稳定（LLM-as-judge 的评分方差大），**"生产环境里的持续验证"是无人区**

**具体场景**：
某股份制银行的"智能信贷初审 Agent"在试点时表现惊艳（审批通过率、材料识别率均达标），但在上线前的 200 例回归测试中，**同一批材料换顺序提交，结论一致性只有 78%**——合规部直接叫停项目，理由是"无法向监管解释为什么同样的材料会得到不同结论"。银行需要一个：**可重复的 Agent 行为测试平台**——沉淀业务场景测试集（含边界与对抗用例），每次模型更新、提示词调整、Agent 框架升级后自动跑全量回归，输出"行为一致性报告"。

另一个场景：某政务服务中心的"办事咨询 Agent"被市民投诉"昨天告诉我要 3 份材料，今天说 5 份"——舆情压力下，管理部门需要**"对话质量抽检 + 一致性监控"工具**：对历史对话定期重放、交叉验证答案稳定性，自动发现"同一问题不同答案"的会话并预警。还有：某 SaaS 公司把 Agent 能力开放成 API 给第三方开发者，**客户反馈"你们的 Agent 时好时坏，我没法写集成测试"**——该公司需要一个"Agent 行为快照/契约测试"机制，让集成方像测试 REST API 一样测试 Agent 行为。

**市场机会**：
- 目标客户：已上线/试点 Agent 的中大型企业（金融、政务、医疗、客服）、Agent 平台与框架厂商（内嵌测试能力）、提供 Agent 服务的 SaaS 公司（需要给客户吃定心丸）
- TAM：对标软件测试与 CI/CD 市场（全球约 $50B）+ AI 质量保证新兴市场（2026 年约 $3-5B 且 CAGR 40%+）；**每一个生产化 Agent 都是这个产品的潜在客户，Agent 生产化率每提升 1%，市场就扩大一圈**
- 付费意愿：企业为"稳定性"付费的意愿极强——一次事故造成的业务与声誉损失远超测试工具年费；定价可参考测试类 SaaS：团队版 $500-2,000/月，企业版 $3,000-15,000/月（含场景测试集共建），单次深度评估项目制 $30-100K
- 竞争空白：现有玩家分散在三个断层——评测基准方做静态榜单不懂生产场景、LLM 监控工具做"日志与成本"不做"行为正确性"、框架厂商内置的 eval 模块浅尝辄止（无回归、无基线、无报告）；**"面向生产 Agent 的持续回归测试与一致性报告"是完整空白**，先发者绑定 2-3 个标杆行业即可建立数据壁垒（测试集即护城河）

### 需求 2：多 Agent 并行开发的版本控制与审计——"五个 Agent 同时改我的仓库，到底谁干的？"

**痛点来源**：
- **开发范式已变，工具没跟上**：atlas（source control for agents）快速冲上 Trending，说明开发者已经开始**同时运行多个 coding agent 并行产出**；但现有 git 工作流是为"人类串行协作"设计的——**agent 的提交没有"意图元数据"（为什么改、基于什么指令、用了什么上下文），冲突时无法判断该信谁的**
- **"谁改的"成为审计刚需**：越来越多企业要求**代码归属可审计**（哪些代码由 AI 生成、由哪个 Agent、基于什么需求）；甲方合同里开始出现"AI 生成代码需可溯源"条款，现有工具完全无法回答
- **回滚粒度太粗**：一个 agent 的 200 次操作里，只有 3 次是错误改动——git revert 只能整块回滚，**没有"操作级撤销"（undo 到某个 agent 的某一步）**；多 agent 并行时，两个 agent 改了同一文件的不同逻辑，合并时互相踩踏，出了 bug 无法定位责任
- **Agent 工作区隔离缺失**：生产级做法应该是"每个 agent 一个隔离工作区，预览确认后再合并"，但主流工具没有这个流程——**并行 agent 直接在主干上乱写，事故不断**

**具体场景**：
某创业公司用 5 个 coding agent 并行重构一个 monorepo（前端 agent、后端 agent、测试 agent、文档 agent、迁移 agent），周五合并后生产环境挂了——**排查两天才知道是"文档 agent"顺手改了一个配置文件的格式导致迁移 agent 的脚本报错**。他们需要：**跨 agent 的变更时间线（谁、何时、为什么、改了什么）+ 冲突归因 + 一键回滚到任意 agent 的任意操作点**。

另一个场景：某银行外包开发团队被审计要求"说明这段 AI 生成代码的来源"——他们需要**每个提交自动携带 agent 签名（agent 身份、指令来源、生成时间、所用模型）**，生成合规报告。还有：某大型软件公司的效能团队想量化"agent 产能"——需要**按 agent 统计变更量、缺陷率、回滚率**的仪表盘，把 agent 当作"团队成员"来管理（对标 DORA 指标）。

**市场机会**：
- 目标客户：重度使用 coding agent 的软件团队、Agent 平台/IDE 厂商（需要内嵌工作台）、金融/政务等强审计行业的技术部门、外包与研发管理方
- TAM：对标版本控制与 DevOps 工具链市场（GitHub/GitLab 生态年收入数十亿美元）；**"Agent 原生"重做版的价值主张更强：不是管理"人类协作"，而是管理"人类-多 Agent 混合劳动力"**——这是下一个十年的开发者基础设施叙事
- 付费意愿：开发者工具付费习惯成熟（团队 $8-19/人/月起步）；企业版的核心卖点是审计合规与风险管理，客单价可达 $20-50K/年；"回滚一次生产事故省下的钱"是现成的 ROI 话术
- 竞争空白：atlas 等开源项目证明需求但只是"个人工具"（无企业特性、无审计、无策略）；GitHub 等平台对 agent 提交的支持停留在"按账号区分"的原始层面；**"agent 意图元数据 + 操作级回滚 + 隔离工作区 + 合规审计"四合一的 Agent 协作管理平台是空白**——窗口期约 6-12 个月，先发者可以借开源（atlas 生态）快速起量再商业化

### 需求 3：本地 MoE 推理民主化——"不买新显卡，跑前沿模型"的隐私与成本双驱动

**痛点来源**：
- **数据不出域的硬约束**：Project Lily 爆料（OpenAI 承包商阅读用户聊天记录）让"数据上云"的信任雪上加霜；医疗（患者数据）、法律（案卷保密）、金融（监管要求）、政务（涉密）行业**对"模型推理必须发生在自己设备上"的需求是刚性的**，但前沿模型动辄几百 GB 显存要求，本地基础设施根本扛不住
- **显存是最大的成本枷锁**：一张 80GB 显存的 GPU 卡数万美元，中小企业买不起、也养不起；**colibri 证明"专家流式加载"可以在普通机器上跑 MoE 模型**——但这类项目还是"极客玩具"，没有产品化：安装门槛、调度优化、多模型管理、API 兼容层全部缺失
- **云 API 的长期成本与依赖**：重度使用场景（持续大批量推理）下云 API 的 token 费用是长期出血点；且**供应商模型更新导致行为变化**，企业希望"锁定一个版本自己部署"——本地部署 = 版本锁定 + 成本可控 + 数据安全，三赢，但被硬件门槛挡住
- **端侧应用的推理需求**：浏览器（WebGPU kernels 200+）、笔记本、边缘设备的本地推理正在从"玩具"走向"应用"，但**模型太大跑不动、太小效果差**——"磁盘/内存换显存"的调度技术是解药，缺的是工程化的中间件

**具体场景**：
某头部律所采购了"案卷分析 Agent"处理数十万页保密卷宗，但律所内网环境不能连外部 API，现有服务器只有 4×24GB 显存——**前沿模型的权重放不下，只能退而用小模型，效果打六折**。他们需要：**一套能在现有硬件上跑大 MoE 模型的本地推理平台**——自动做专家流式调度、显存/磁盘/内存三级缓存、推理加速，效果接近云端但数据完全不出域。

另一个场景：某三甲医院的信息科想部署"病历质控 Agent"，但采购 8 卡 A100 的预算被砍——他们需要**"消费级 GPU 服务器就能跑"的分诊/质控模型方案**，并且要求像软件一样"双击安装、图形化管理"。还有：某出海 App 团队想在用户手机端做"离线智能助手"，模型 7B 太大、1.5B 太笨——**需要"按设备能力动态切分/流式加载"的边缘推理 SDK**（手机存储几百 GB，磁盘换显存的思路在端侧同样成立）。
