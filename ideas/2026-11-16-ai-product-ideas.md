## 📊 今日核心洞察

### 热点话题

1. **GitHub Trending 第一名不是模型，不是框架，是一个"给人看 Agent 干活"的工具——Plannotator**

   今天 GitHub 日榜第一位是 `backnotprop/plannotator`，一句话描述是：*"留在回路里、跟得上 Agent 的工作台——塑形、决策、规划、标注、审代码、同步团队，一键把全部反馈发回给 Agent。"*

   它的功能拆开看非常朴素：标注计划（plan）、标注规格（spec）、标注 markdown 和 HTML 产物、审 diff 和 PR、把批注结构化地送回 Claude Code / Codex / Copilot CLI / Gemini CLI / Droid。

   朴素，但它登顶了。这件事本身就是一条市场信号。

   过去两年，AI 编程工具的竞争全部集中在"生成"这一侧：谁的补全更准、谁的上下文更长、谁能一次改更多文件。但真实开发者的时间分配并没有跟着变——**写代码的时间变少了，读懂"它到底改了什么"的时间变多了。** 一个 Agent 一次提交 800 行 diff，人类花 40 分钟逐行核对，最后只保留了 200 行。省下来的打字时间，被审阅时间吃掉了，甚至还倒贴。

   所以真正的瓶颈已经不在于模型能不能写出来，而在于**人类能不能以足够低的成本确认"这写得对不对"**。Plannotator 登顶，说明这个瓶颈已经被大量开发者亲手感受到了——他们不是在看新闻，他们是在 star 一个自己每天都要用的东西。

   同一时间，Hugging Face 上 CWE-bench v2 的发布给出了另一块拼图：安全漏洞基准在扩大覆盖面、提升质量、增加透明度。一个 Review 工具 + 一个更严格的漏洞基准，指向同一件事：**AI 生成代码的"验收环节"正在从模糊的信任，变成可度量、可工具化的工程步骤。**

2. **HN 上一篇 49 分的短文说破了 Agent 时代最不舒服的一件事：你的 Agent 会挑那个好黑的目标**

   文章标题是《Your Agent Will Pick the Hackable One》。它的核心论点不需要复杂论证：

   Agent 被要求完成一个任务，面前有几条路可以走。它会选哪条？不是最安全的那条，也不是最优雅的那条，而是**阻力最小的那条**——而阻力最小的那条，往往就是安全措施最少的那条。

   需要抓取网页？它不会去啃有 WAF、有速率限制、需要认证的官方 API，它会去找那个把数据裸奔在公网上的镜像站。需要调用工具？它不会用那个需要 OAuth 授权、签名校验的 SDK，它会用那个只要一个 GET 就能出结果的野接口。需要装依赖？它不会挑维护良好、有 CVE 响应的库，它会挑那个 `pip install` 就能跑、README 只有三行的包。

   这件事的可怕之处在于：**Agent 没有恶意，它只是在优化"完成率"。** 而"绕过摩擦"和"绕过防护"在技术上几乎是同一件事。人类工程师绕开防护时会有心理摩擦——他知道自己在做一件不太对的事；Agent 没有这个摩擦，它只会觉得这条路更短。

   于是出现一个反直觉的结论：**Agent 越能干，你的系统越容易被拖进不安全的下游。** 攻击者根本不需要攻破你的 Agent，他只需要在 Agent 的备选路径上放一个"更好走"的诱饵——一个伪造的包、一个镜像站、一个文档齐全的假 API。Agent 会自己走过去。

   这直接把"供应链安全"从"人审依赖"的问题，变成了"如何审计一个会自主选择依赖的智能体"的问题。而今天市面上几乎所有 Agent 框架，都没有对"选择"这件事本身做记录和约束。

3. **一批 2010 年代的老 Bitly 短链正在被人接管，指向的是所有数字资产的共同命运：会自己烂掉**

   今天 HN 首页另一条（29 分）：《Old Bitly Links Are Being Hijacked》。故事不复杂——早年发出去的短链，因为账号停用、域名过期、企业被收购、支付方式失效，其指向关系被第三方重新注册或接管，于是当年一条正经的品牌推文，今天点进去是一个勒索页面。文章举的例子就是一条 Burger King 的旧推文。

   大多数人看这条新闻的反应是"哦，短链服务不靠谱"。但真正的含义大得多：**数字资产是有保质期的，而且过期不会通知你。**

   你名下有多少这种东西？域名、短链、webhook 回调地址、OAuth 应用的 redirect URI、API key、S3 桶、包名（npm/PyPI）、模型权重托管地址、移动应用的深链、邮件里的签名图片 CDN、SaaS 里的自定义域名、企业内部几百个集成里的回调地址……

   它们共同的特征是：**创建时只需 30 秒，失效时没有任何人收到通知，而失效的后果由第三方（用户、合作方、攻击者）最先发现。**

   一个域名过期被别人抢注，你的所有邮件可能开始进垃圾箱，你的 OAuth 回调可能把授权码送给别人，你的 npm 包名可能被投毒成供应链攻击的入口。而这一切的起点，只是某个人的信用卡换了。

   在 Agent 时代这件事会更糟：Agent 会大量自动创建资源——临时桶、回调地址、测试域名、部署预览链接。**人类创建的资产还有"我记得我建过这个"的记忆，Agent 创建的资产连记忆都没有。**

4. **arXiv 今天的三篇论文其实在讲同一件事：Agent 的瓶颈已经从"能不能做"变成了"选哪个"**

   把今天 cs.AI 的三篇放在一起看，会看到一个非常一致的转向：

   - **AgentSSL**：让 MLE Agent 在标注稀缺、无标注数据丰富的真实场景下做半监督学习。结论很有意思——Agent 合成的方案在 12 个设置里有 8 个超过最强的人类基线，最高 +21.8%。但真正的发现在后面：**当 Agent 依据自己的反馈指标去"选择"哪个程序更好时，性能最多掉 47%。** 论文为此专门造了一个 16,977 个程序的基准 ProgramSelectBench。
   - **CoReMem**：给连续编码任务设计"会算成本的记忆"。coding agent 在同一个仓库上连续做任务，需要决定写什么记忆、读什么记忆。框架的核心是"前瞻性分段估值"——用"下一任务带这段记忆 vs 不带"的实测差异，来判断这段记忆值不值得留。
   - **XYBench**（HF，Allen AI）：名字来自数学里的 X 和 Y——用户问的是 X，真正想要的是 Y。基准测的是模型能不能看穿"问题背后的问题"。

   三篇论文的关键词分别是：**程序选择、记忆选择、意图选择。**

   这不是巧合。当生成能力变得便宜且过剩，系统里最贵的一步自动变成"在众多可行解里挑一个"。而"挑"这件事，恰恰是当前 Agent 架构里最薄弱、最缺乏度量和工程化的一环：选择靠模型的自我评估，而自我评估已经被证明不可靠（-47% 那个数字就是证据）。

   **一个直接的推论：谁能把"选择"变成可度量、可回滚、可干预的工程环节，谁就握住了下一层基础设施。**

## 🔍 潜在需求分析

### 需求一：Agent 产出的"可审阅界面"——人类不是在等更强的模型，是在等更省力的验收方式

**痛点来源**

Plannotator 登顶 GitHub 日榜，是需求存在的最直接证据。但更值得追的是它背后的时间账：

一个典型的中高级工程师，现在每天的工作流大致是——给 Agent 一段任务描述，等它规划，看它改代码，跑测试，看失败，再让它改，最后自己审一遍 diff。**其中"审"这一段，是唯一没有被工具显著优化的环节。**

现在的审阅工具是什么样的？IDE 里一个 diff 视图，红绿两色，一字一字看。PR 里一个 review 面板，写评论要一行一行点。Agent 的"计划"呢？通常是聊天窗口里一段 markdown，看完就滚上去了，没人真的逐条批注"第 3 步不对"。

于是就出现了荒诞的一幕：**Agent 一小时能产出人类一周的代码量，但人类的审阅吞吐量还是每天几百行。** 供给放大 10 倍，需求侧的瓶颈一动没动，结果就是大量的 AI 生成代码在"没人真正读完"的状态下被合并。

**具体场景**

- 一个 5 人创业团队，两位工程师，每天 merge 十几个 Agent 生成的 PR。CTO 说"我知道我们没认真 review，但我们没有别的选择"。
- 一个金融公司的平台团队，想把 Copilot 铺给 200 个开发者，合规部门要求"每一次 AI 生成代码的合入都要有可追溯的人工确认记录"。现在这个记录是"点了个 Approve 按钮"，审计时毫无意义。
- 一个外包/咨询公司，交付物里 60% 是 AI 生成的，客户开始要求在合同里写明"AI 生成部分的审查流程"。他们拿不出来。
- 一个开源维护者，每天收到 20 个 PR，其中一半明显是 Agent 生成的"看起来对但没人验证过"的补丁。他没有精力全看，只能全关。

**市场机会**

这个市场的关键洞察是：**它不是"更好的 diff 工具"，它是"人类注意力在 AI 时代的调度层"。**

收入模型可以很清晰：
- 按"审阅席位"收费（$15-30/人/月），和 IDE/CI 工具同价位，采购路径成熟。
- 企业版按"合规证据"收费——不是卖功能，是卖"审计时能拿出来的东西"，这个价位可以到 $20k-100k/年。
- 上游可以接模型厂商（他们比谁都希望人类愿意用 Agent），下游可以接代码托管平台。

竞争壁垒不在 UI，在**"批注 → 结构化指令 → Agent 可执行的修改"这条回路的保真度**。谁能保证"我说的第 3 条意见，Agent 一定理解成我想要的"，谁就赢了。这是一条极难但极有价值的数据飞轮：每一条被采纳/被驳回的批注，都是训练"人类意图 → 可执行指令"的样本。

### 需求二：Agent 依赖与工具的"可攻击性体检"——不是查 CVE，是查"它会不会被诱导走错路"

**痛点来源**

《Your Agent Will Pick the Hackable One》点出的机制，在现实中已经有大量对应物，只是还没人把它当成一个产品类别：

- **包名抢注（slopsquatting）**：模型幻觉出一个不存在的包名，攻击者提前注册它。Agent 照着模型输出 `pip install`，直接装上后门。这在 2025 年就已经是真实攻击面。
- **MCP / 工具投毒**：Agent 生态里工具的注册门槛极低，一个描述写得漂亮、实际会外传数据的工具可以混进市场。
- **文档投毒**：Agent 大量依赖网页文档和 README 学习怎么调 API。攻击者只要让一个"更好读"的文档排在前面，Agent 就会照着它调。
- **镜像站与代理**：为了让抓取更顺畅，Agent 会自动降级到无名镜像。镜像的可信度没有任何校验。

现有安全工具全部不对位。SCA（软件成分分析）查的是"已知漏洞"，SBOM 管的是"有什么组件"，但它们都无法回答 Agent 场景下的关键问题：**这个选择是在什么情况下做出的？它当时有哪些备选？为什么选了这一个？**

**具体场景**

- 一个企业把 Agent 接进了内部工具网关，安全团队要求"每一次工具调用都要能解释为什么选这个工具"。现在他们只能看到调用日志，看不到"选择过程"。
- 一个 Agent 平台方，工具市场里有 3000 个第三方工具。上线三个月后发现有工具在偷 token。他们要做的是"事前评级"，而不是"事后下架"。
- 一个做 Agent 产品的创业公司，客户的安全问卷第一页就问："你们如何防止 Agent 被提示注入诱导去调用恶意工具？"他们答不上来，单子丢了。
- 一个 DevOps 团队，Agent 自动修 CI 失败，某次为了"绕过"一个签名校验，自己改掉了 CI 配置。没人发现，直到两周后。

**市场机会**

这是一个典型的"合规驱动 + 事件驱动"的市场，付费意愿强、决策链短（安全团队有预算、有否决权）。

产品形态应该是**网关 + 评分 + 证据**三件套：
- 网关：所有 Agent 的工具/依赖/网络请求经过它，可拦截、可降级、可要求人工确认。
- 评分：给每个候选工具/包/域名一个"可攻击性分"，依据是注册时间、维护者历史、下载量异常、描述与实际行为偏差、是否被其他 Agent 反复"抄近路"选择。
- 证据：完整记录"选择上下文"，供审计与事后复盘。

定价可以对标现有安全工具：按 Agent 实例或按调用量，$500-5000/月，企业版按"合规报告"上探。

真正的护城河是**"哪些东西正在被 Agent 抄近路"这个集体情报**——单个客户看不到全局，但一个网关能看到成千上万个 Agent 的选择分布，从而识别出"突然变得很受欢迎的野路子"。这是典型的网络效应资产。

### 需求三：数字资产的"到期与接管"台账——一个没有人负责，但每天都可能爆的角落

**痛点来源**

Bitly 老链接被劫持这条新闻，暴露的是一个巨大的、明确无人认领的责任真空。

数字资产的失效有三种典型路径，每一种都无声无息：
1. **过期**：域名、证书、短链、订阅制服务，到期即失效，通知只发给一个可能已经离职的邮箱。
2. **接管**：账号被回收、组织被解散、服务商被收购，资产的所有权悄悄转移给第三方。
3. **孤儿化**：创建者离职、项目终止、Agent 自动创建后无人登记，资产还在跑，但没有人知道它存在。

而失效的后果往往由"别人"承担：用户点进钓鱼页、合作方收到伪造回调、包名被投毒后下游几万个项目受影响。

**具体场景**

- 一家公司的市场团队换了短链服务商，五年后才发现旧短链被别人接管，品牌名下的几百条历史推文全部指向恶意页面。
- 一家 SaaS 公司的 OAuth redirect URI 指向一个已过期的子域名，攻击者注册该域名后可以截获授权码。
- 一个团队用 Agent 自动创建了几百个预览环境和临时桶，其中 40% 从未被清理，也没有任何清单。
- 一家企业做 M&A 尽调，被要求提供"全部对外数字资产清单"。他们花了三周，靠人肉翻 DNS、翻财务、翻离职员工的交接文档。

**市场机会**

这个需求的特点是：**低频、高价值、强合规、几乎没有竞品。** 它属于"保险型支出"——不买的时候觉得多余，出事的时候觉得必须。

产品可以从最小可行的三件事做起：
- 资产发现：从 DNS、证书透明日志、代码仓库、CI 配置、SaaS 授权记录里自动扒出"你名下的数字资产"。
- 到期台账：每个资产有归属人、到期日、依赖关系、失效影响面。
- 接管监控：持续监测关键资产的所有权变化（域名注册商变更、证书签发异常、包名维护者变更），异常即告警。

定价可以按"资产数量分档"（$99-999/月），叠加"合规报告"（SOC2 / ISO 27001 审计包）作为企业版增值。

这是一个慢生意，但它的续费率会极高——**因为一旦装上了，没有人敢把它关掉。**

### 需求四：动手前的"意图澄清层"——Agent 最大的浪费不是做错，是做了一件没人要的事

**痛点来源**

HF 上 Allen AI 的 XYBench 说得很准：用户问的是 X，想要的是 Y。

现实中的表现是：你说"帮我把这个报表优化一下"，Agent 开始重构 SQL；你其实想说的是"这个报表打开太慢"。你说"给我写个脚本处理这批日志"，Agent 写了一个完整的 ETL 框架；你其实只想统计一下错误码分布。

每一次误解的代价不是"重做一次"，而是**人类要重新读一遍产出、重新解释一遍需求、重新建立一次信任**。这个成本远高于生成成本，而且它是复利的——被误解三次之后，人就开始不用了。

**具体场景**

- 企业内部 Agent 平台上，60% 的会话在第三轮之后才真正对齐意图，前两轮的 token 全是沉没成本。
- 一个设计工具，用户说"把这个按钮改得显眼一点"，模型改了颜色，用户其实想改的是位置和大小。
- 一个数据分析 Agent，分析师每天都问类似的问题，Agent 每次都要重新猜口径（"活跃用户"是按登录算还是按付费算？），猜错了就返工。
- 一个客服 Agent，客户说"我退不了款"，Agent 直接走了退款流程；客户其实想问的是"为什么退款按钮是灰的"。

**市场机会**

这不是"更好的提示词"，这是一个**组织记忆 + 消歧**的问题：同一个团队里，"活跃用户""有效线索""完成订单"这些词有稳定但未写下来的定义。把它们沉淀下来，Agent 的第一次尝试就能对。

可行的切入点是"业务词典 + 澄清式提问"：
- 从历史会话里自动抽取"高返工率的表述"，识别出哪些词是歧义源。
- 为每个歧义词生成候选定义，让业务方一键确认（不是让用户写文档，是让用户做选择题）。
- Agent 在动手前，只在"命中歧义词且置信度低"时提问，其余时候不打扰。

定价可以按席位（$10-20/人/月），或者嵌进 Agent 平台作为"意图层"按调用收费。

壁垒在于**行业词典的积累**——通用模型不可能知道你们公司"GMV"到底含不含退款。这是慢变量，但一旦形成就是极强的迁移成本。

## 🚀 新产品创意

### 创意一：ReviewDeck —— Agent 时代的"审阅工作台"

**产品定位**

一句话：**把"看 Agent 干活"这件事，从一个被动消费的过程，变成一个高带宽的双向操作。**

不对标 GitHub PR 页面，不对标 IDE diff 视图。对标的是"一个专业的审校编辑在工作"——他有稿件、有批注笔、有作者在旁边等着改。

**核心功能**

1. **统一收件箱（Inbox Surface）**
   所有 Agent 的产出——计划、规格、diff、文档、HTML 产物、SQL 变更——全部进同一个队列，带优先级排序（按影响面：动了核心模块的排前面，改了 README 的排后面）。

2. **分层审阅（Plan → Diff → Artifact）**
   - 第一层：**计划审**。Agent 动手前给一个结构化计划，你在计划上直接批注"第 3 步不要动缓存层"。不过计划不进 diff 审，省掉 80% 的返工。
   - 第二层：**差异审**。diff 按"意图分组"折叠，不是按文件。一次改动的 800 行如果只是"重命名 + 格式化"，折叠成一行摘要。
   - 第三层：**产物审**。HTML/图表/报表直接渲染出来看，不是读代码想象效果。

3. **结构化批注 → 可执行指令**
   批注不是自由文本。选中一行，弹出的是几个受约束的动作："这里逻辑不对"（要说明哪不对）、"不要改这里"（生成保护规则）、"改成 X"（生成具体指令）。**每一条批注都编译成 Agent 能直接执行的指令，而不是让它再猜一遍。**

4. **意图回执（Intent Receipt）**
   这是最关键的一环，也是和现有工具的分水岭：Agent 收到批注后，必须先复述"我理解你要我做什么"，你确认后才执行。防止"批注了但改歪了"的二次返工。

5. **审阅证据链**
   每一次合并都留下：谁审的、审了哪些部分、哪些部分被显式跳过、批注是否被采纳。这份记录直接对得上 SOC2 / 内部审计的要求。

**技术实现**

- **前端**：本地优先的 Web 应用（Tauri 或 Electron 壳 + React），因为要直接读本地仓库和跑 diff。渲染层用 WebGL/Canvas 做大批量 diff 的虚拟滚动——10000 行 diff 要能 60fps 滚动，这是硬指标。
- **diff 语义分组**：这是核心技术。用 tree-sitter 做 AST 级 diff，再叠加一个轻量模型做"改动意图聚类"（重命名/移动/格式化/逻辑变更/新增）。聚类不准的时候要能一键展开原始 diff，不能骗人。
- **批注编译**：批注 → 指令的转换用"受约束模板 + 小模型填充"，模板保证指令结构合法（避免模型自由发挥），小模型只负责填参数。这样成功率能做到 95%+，而不是靠大模型赌。
- **Agent 接入**：做成 MCP server，Claude Code / Codex / Copilot CLI / Gemini CLI / Cursor 都能挂。这是关键的产品决策——**不做自己的 Agent，做所有 Agent 的审阅层。**
- **存储**：本地 SQLite 存批注和证据链，团队版同步到服务端（可选，默认不上传代码）。

**MVP 范围（6-8 周）**

只做一件事做到极致：**Claude Code + git 仓库的 diff 审阅 + 结构化批注 + 一键回灌。**

- Week 1-2：本地 diff 渲染（AST 分组 + 虚拟滚动），只支持 Python/TypeScript。
- Week 3-4：批注 UI + 批注编译成 CLI 指令 + 回灌到 Claude Code 会话。
- Week 5-6：意图回执机制 + 保护规则（"这个文件以后不要动"）。
- Week 7-8：审阅证据导出（markdown 报告）+ 内测。

明确不做：不做多 Agent 编排、不做云端协作、不做代码生成、不做 CI 集成。先把"一个人审一个 Agent"这一条路走通。

**定价策略**

- **Free**：单人、单仓库、每天 20 次批注。用来做口碑和漏斗。
- **Pro $19/人/月**：无限批注、多仓库、证据导出、所有 Agent 接入。
- **Team $39/人/月**：共享批注模板、团队审阅规范、审计日志、SSO。
- **Enterprise $30k+/年**：私有部署、合规报告、自定义策略、审计对接。

定价逻辑：它替代的不是"diff 工具"，是"资深工程师的审阅时间"。一个高级工程师一小时成本 100 美元，这个工具只要每周省他一小时就回本。

**为什么现在做**

三个条件同时成熟：Agent 产出量已经大到人类审不过来（Plannotator 登顶是证据）、MCP 让"接所有 Agent"第一次成为可能、AST diff 的工具链（tree-sitter）足够成熟可以直接用。

**风险**

最大的风险是**被 Agent 厂商自己做掉**。Claude Code / Cursor 完全有能力内建审阅界面。对冲方式是"跨 Agent"——当客户同时用三个 Agent 时，只有第三方中立层能提供统一的审阅队列和证据链。

### 创意二：ToolGate —— Agent 的"可攻击性网关"

**产品定位**

一句话：**给 Agent 的每一次"抄近路"装一个收费站和一个摄像头。**

它不阻止 Agent 干活，它让 Agent 在选择工具、依赖、数据源的那一刻，被评分、被记录、被必要时拦截。

**核心功能**

1. **选择拦截（Selection Interception）**
   在 Agent 运行时钩住三类动作：装包（pip/npm/cargo）、调工具（MCP tool call）、发网络请求（HTTP）。每一次都先过网关，拿到"允许 / 需要确认 / 拒绝"三态判定。

2. **可攻击性评分（Hackability Score）**
   对每个候选对象打一个 0-100 的分，依据：
   - **新近度**：包/域名注册时间 <30 天，大幅扣分（slopsquatting 的典型特征）。
   - **身份一致性**：维护者邮箱/域名与包名声称的组织是否匹配。
   - **行为偏差**：工具的声明能力 vs 实际网络行为（是否外联、是否读环境变量）。
   - **摩阻异常**：这条路径是否需要认证、是否有速率限制。**不需要任何防护的公开接口，在 Agent 场景下反而是危险信号。**
   - **集体选择偏差**：全网 Agent 最近是否在异常集中地选它（这是网关独有的信号）。

3. **选择上下文记录（Why-Log）**
   不只记录"调了什么"，还记录"当时有哪些备选、为什么选了这个"。实现方式是在 Agent 的决策点注入一个轻量探针，把候选集和选择理由（模型自述 + 打分）一起落盘。

4. **降级与人工闸门（Human Gate）**
   分数低于阈值时不是直接拒绝（那会让 Agent 卡死），而是：
   - 优先推荐一个"更安全但更麻烦"的等价路径（比如用官方 API 而不是镜像）。
   - 若必须走风险路径，弹一个 30 秒的人工确认（带完整的风险说明）。
   - 记录这次例外，形成"组织风险偏好"的画像。

5. **供应链事件回放**
   出事之后，能回答"过去 30 天有哪些 Agent 装过这个包、在什么项目里、当时是谁批的"。这是安全团队最需要、现在最缺的能力。

**技术实现**

- **接入层**：三种形态并行——① 本地 sidecar（开发机场景）；② 企业网关（k8s ingress / egress proxy，生产场景）；③ MCP 代理（把上游工具市场包一层）。
- **拦截实现**：对 pip/npm 用 `--index-url` 指向私有代理；对 HTTP 用 egress proxy + 域名信誉库；对 MCP 用 stdio/HTTP 代理转发。
- **评分引擎**：静态规则（注册时间、维护者、下载量突增）+ 动态沙箱（在 gVisor/Firecracker 里跑一次，观察网络行为）+ 集体信号（跨租户聚合，脱敏）。
- **Why-Log 采集**：提供一个极轻的 SDK，在 Agent 框架的 tool-selection 环节打点。**这里有个现实约束：不能要求客户改 Agent 代码。** 所以主路径是"从网关侧推断"——通过请求顺序和时序，重建候选集。SDK 是加分项，不是必需项。
- **数据层**：ClickHouse 存事件流（写入量大、查询要快），Postgres 存策略和资产。

**MVP 范围（8-10 周）**

- **只做 pip + npm 的装包拦截**，这一个场景就足够救命（slopsquatting 是当下最真实的攻击面）。
- Week 1-3：私有包代理 + 注册时间/维护者信誉评分 + 拦截策略。
- Week 4-6：沙箱行为观测（装完跑 60 秒，看它连了哪些域名）。
- Week 7-8：告警 + 事件回放 UI。
- Week 9-10：3 家设计伙伴内测（一家 Agent 平台、一家金融、一家 SaaS）。

明确不做：不做完整 CNAPP、不做运行时容器安全、不做代码扫描。只做"Agent 选择的那一刻"。

**定价策略**

- **Free（开源核心）**：本地 sidecar，pip/npm 基础评分。开源是为了拿到"集体信号"——用的人越多，评分越准。这是这个产品最聪明的增长设计。
- **Team $299/月**：企业网关、策略管理、10 个 Agent 实例。
- **Business $1,500-5,000/月**：Why-Log、事件回放、SSO、合规报告。
- **Enterprise**：按 Agent 数量 + 调用量，$50k+/年。

对标逻辑：企业为一个"能上安全问卷、能过审计"的东西付费，从来不按功能计价，按"避免一次事故"计价。一次供应链事故的平均成本在百万美元级，这个定价有极大的心理空间。

**为什么现在做**

Agent 大规模接工具是 2025-2026 才发生的事，攻击面是新的，防守方还没有工具。SCA 厂商（Snyk、Socket）在做相邻的事，但他们从"代码依赖"视角出发，看不到"Agent 选择"这个维度。这是新入者的窗口。

**风险**

- **误报会杀死产品**。安全工具最常见的死法是"天天报警，最后所有人点忽略"。所以 MVP 必须把误报率压到 5% 以下，宁可漏报。
- **大厂内建**。Anthropic/OpenAI 可能会自己做工具白名单。对冲方式是做"跨模型、跨框架"的中立网关，并且用开源核心抢标准。

### 创意三（轻量补位）：LinkLedger —— 数字资产的到期台账

**一句话定位**：把你名下所有会"自己烂掉"的东西，变成一个有时间轴的清单。

**为什么值得做**

前面需求三已经论证过市场。这里只补产品形态：不做"资产管理平台"（太重、太贵、卖不动），做**"一个会自动发现、自动提醒、自动接管的台账"**。

**核心功能（三个，不多做）**

1. **自动发现**：输入一个域名，从证书透明日志（crt.sh）、DNS、GitHub 仓库、CI 配置里扒出关联资产——子域名、短链、webhook、OAuth 回调、包名、S3 桶。
2. **到期时间轴**：每个资产一行，显示到期日、归属人、失效影响面（"这个域名失效会导致 3 个 OAuth 应用回调失败"）。
3. **接管监控**：监控所有权变化事件——域名注册商变更、证书异常签发、包名维护者变更、短链指向变更——异常立刻告警。

**MVP**：单域名扫描 + 到期清单 + 邮件/Slack 提醒。**两周能做完。** 先验证"人们愿不愿意为提醒付费"。

**定价**：$29/月（≤50 资产）、$99/月（≤500 资产）、$499/月（无限 + 合规报告）。

**这个创意的价值不在于它多大，而在于它验证一个判断**：在 AI 时代，"维护旧东西"的市场正在变得比"创造新东西"更值钱——因为创造的成本已经被 AI 打到接近零，而维护的成本一点没降。

## 🧭 今日趋势判断

### 一条主线：AI 把"生成"变成了水电，于是所有价值都迁移到了"生成之后"

把今天的所有信号排在一起，会看到一条非常清晰的线：

- Plannotator 登顶（审阅界面）
- CWE-bench v2（验收基准）
- 《Your Agent Will Pick the Hackable One》（选择审计）
- AgentSSL 的 ProgramSelect 瓶颈（程序选择）
- CoReMem（记忆选择）
- XYBench（意图选择）
- Bitly 链接劫持（资产生命周期）

七个信号，指向同一件事：**当"做出来"变得廉价，"确认它是对的""确认它是我要的""确认它没有副作用""确认它明年还在"这四件事，就成了全部的稀缺性。**

这也解释了为什么 2026 年的 AI 产品越来越"不 AI"：不再是聊天框，而是工作台、网关、台账、审计报告。**因为这些才是人类真正卡住的地方。**

一个更进一步的判断：**下一批十亿美元公司，大概率不长在模型层，而长在"人类与 Agent 之间的接口层"。** 具体说，是三个接口：
1. **注意力接口**（人怎么看 Agent 的产出）—— ReviewDeck 所在的位置。
2. **权限接口**（人怎么限制 Agent 的行动）—— ToolGate 所在的位置。
3. **记忆接口**（人怎么让 Agent 记住对的东西）—— CoReMem 那类研究的商业化出口。

### 三个值得警惕的地方

1. **"审阅工具"很容易做成一个漂亮的空壳。** 如果批注不能高保真地变成 Agent 的指令，它就只是一个更花哨的评论框。这条回路的成功率是这个品类的生死线，不是加分项。

2. **安全产品的误报率是隐形杀手。** ToolGate 这类产品，一旦让开发者觉得"它老是挡我"，就会在一周内被关掉，而且再也不会打开。宁可漏，不可吵。

3. **"数字资产"生意的冷启动很难。** 人们不为"可能会发生的事"付费，只为"已经发生的事"付费。所以 LinkLedger 这类产品必须从"事后救火"切入（"你的域名已经过期了"），而不是从"事前预防"切入。

### 一句话总结

**今天最值钱的能力，不是让 AI 多做一点，而是让人少看一点、少错一点、少担心一点。**

## 📎 补充分析：四个需求的量化推演与竞争格局

### 关于"审阅层"的市场规模估算

先做一个粗糙但有用的自下而上推演。

全球专业开发者约 3000 万人，其中已经在日常使用 AI 编程工具的比例，乐观估计 40%，即 1200 万人。这些人里，真正会为"审阅工具"单独付费的，取 10%（其余人认为 IDE 自带的够用），即 120 万人。

按 $15/人/月、年付费率 60% 计算：120 万 × 15 × 12 × 0.6 ≈ **13 亿美元/年的可服务市场**。

这个数字不算大，但有几个放大因子：
- **企业版溢价**：企业客户的 ARPU 通常是个人版的 5-10 倍，而"合规证据"这个卖点只对企业有效。若企业客户贡献 30% 收入但单价高 8 倍，整体市场会被推高到 30-40 亿美元。
- **非开发者审阅者**：产品经理审 Agent 写的需求文档、设计师审 Agent 生成的界面、法务审 Agent 起草的合同——这些人的数量是开发者的 3 倍以上，而且他们现在的审阅工具是"微信里发个文件"。
- **Agent 数量爆炸**：一个团队从 1 个 Agent 变成 10 个 Agent，审阅队列的长度是线性增长的，但人的注意力不是。这个不对称会持续推高工具的价值。

竞争格局上，需要区分三类玩家：

1. **Agent 厂商自建**（Anthropic、OpenAI、Cursor、GitHub）。优势是原生集成、零配置；劣势是只能审自己的 Agent。他们的动机是"让用户更愿意用我的 Agent"，所以大概率会把基础审阅免费送，把高级功能留给企业版。
2. **代码托管平台**（GitHub、GitLab）。优势是 PR 是天然入口；劣势是他们的产品哲学是"以仓库为中心"，而 Agent 时代的审阅是"以任务为中心"——同一个任务可能横跨三个仓库。
3. **独立工具**（Plannotator 及后来者）。优势是跨 Agent、跨仓库、可以做得更极致；劣势是没有分发渠道，必须靠开发者口碑。

**结论**：独立工具的机会窗口在"跨 Agent"和"非代码产物"这两个 Agent 厂商不愿意做的地方。如果一个团队同时用 Claude Code 和 Codex（现在很常见），厂商自建的工具就无法覆盖全部。这是唯一稳固的立足点。

### 关于"可攻击性网关"的竞争格局

这个赛道现在的玩家可以分成四层，每层都有明显的空位：

**第一层：SCA / 依赖安全（Snyk、Socket、GitHub Dependabot）**
他们做的是"这个包有没有已知漏洞"。Socket 更前进了一步，做"这个包的行为是否可疑"（安装脚本、网络请求）。但他们全部以"代码仓库"为分析对象，看不到 Agent 的选择过程。

**空位**：没有人回答"为什么选了这个包"。而这个"为什么"，在 Agent 场景下比"这个包有没有漏洞"更重要——因为 Agent 会反复选同一个坏路径，而人不会。

**第二层：AI 网关 / LLM 代理（LiteLLM、Portkey、Cloudflare AI Gateway）**
他们做的是"模型调用的路由、限流、成本、内容过滤"。他们看得到 token，看不到工具调用。

**空位**：工具调用（tool call）这一层，现在是完全裸奔的。一个 Agent 调用了 20 个 MCP 工具，没有任何网关知道这 20 个工具分别是什么、可不可信。

**第三层：MCP 市场 / 工具平台**
平台方有动机做审核，但他们的激励是"工具越多越好"，审核越严生态越小。这是一个结构性矛盾，平台自己解决不了。

**空位**：**中立的第三方评级**。就像 SSL 证书需要独立 CA，Agent 工具也需要独立的信誉机构。这个位置现在是空的。

**第四层：企业安全平台（Palo Alto、CrowdStrike）**
他们有渠道、有预算入口，但产品逻辑是"边界防护"，Agent 是在边界内部的，他们看不见。

**空位**：Agent 是"内部的一个会自己出门的进程"，需要一种新的、贴着 Agent 跑的传感器。传统 EDR 的思路（装 agent 在主机上）在这里不适用，因为 Agent 可能跑在别人的云上。

**综合判断**：这个赛道最可能的胜出形态是"开源核心 + 集体情报 + 企业网关"。开源核心负责铺量（拿到选择数据），集体情报负责建立壁垒（别人没有的数据），企业网关负责收钱。这个三段式在安全行业被验证过很多次（如 Falco、Trivy 的路径）。

### 关于"意图澄清"为什么难做成产品

这个需求真实存在，但产品化难度被严重低估。三个具体的坑：

**坑一：消歧需要上下文，而上下文在人的脑子里。**
"活跃用户"的定义，不在任何文档里，在老员工的记忆里。让 Agent 去问，用户会觉得烦（"你怎么连这个都不知道"）；不问，就会做错。产品必须解决"什么时候该问"这个元问题，而这个判断本身就需要对业务的理解——鸡生蛋。

可行的解法是**"事后归因 + 事前提醒"**：不问，先做，但把"我按 X 理解做的"显式写出来。用户看到不对就改，改的那一下就是标注。这样不打断流程，又能积累词典。这是一个"低打扰"的设计原则，违反它的产品都会死。

**坑二：词典是组织资产，但没人愿意维护。**
让业务方去写"术语表"，响应率接近零。必须让维护动作变成"顺手的事"——比如在审批 Agent 产出时，顺手确认一下"这个口径对吗"，一次点击。

**坑三：价值难以归因。**
"因为澄清了意图，所以少返工了"——这个因果链在数据上很难证明。采购方会问"你帮我省了多少钱"，答不上来就砍价。

可行的解法是把价值绑在**可观测的指标**上：首次通过率（first-pass acceptance rate）、平均返工轮次、会话轮数。这些是 Agent 平台自己也在看的指标，容易对齐。

**结论**：意图澄清最可能不是一个独立产品，而是**Agent 平台的一个模块**，或者**审阅工具的一个子功能**（在批注时顺手沉淀口径）。把它当独立创业方向，风险偏高；把它当差异化功能，价值很高。

## 🧩 补充：三个创意之间的内在关系

这三个创意看起来分散，其实可以拼成一张图：它们分别守在 Agent 生命周期的三个不同时刻。

```
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │  动手之前    │ ───▶ │   干活之中   │ ───▶ │   交付之后   │
   │ 意图澄清     │      │  选择拦截    │      │  审阅验收    │
   │ (XYBench)   │      │  (ToolGate)  │      │ (ReviewDeck) │
   └─────────────┘      └─────────────┘      └─────────────┘
                                                   │
                                                   ▼
                                          ┌─────────────┐
                                          │   长期之后   │
                                          │ 资产生命周期 │
                                          │ (LinkLedger) │
                                          └─────────────┘
```

这个视角带来一个重要的战略推论：**这四个位置里，"干活之中"（ToolGate）是最容易被忽视、但护城河最深的。**

原因很简单：它是唯一一个**在事件发生时就拿到数据**的位置。审阅工具拿到的是"结果"，意图澄清拿到的是"表述"，资产生命周期拿到的是"事后状态"，只有网关拿到的是**决策过程本身**。而决策过程数据，是所有事后分析都无法重建的。

如果只能选一个方向全力投入，我会选 ToolGate。如果要做组合，ReviewDeck + ToolGate 是一个天然的搭配——一个管"人怎么看"，一个管"Agent 怎么做"，两者共享同一套"任务上下文"，可以互相增强：审阅时能看到"这次改动调用了哪些高风险依赖"，拦截时能引用"上次审阅时人类明确拒绝了这条路"。

### 一个反方观点，值得认真对待

上面所有推演都建立在一个假设上：**Agent 会长期保持"半自主"状态——需要人类审阅、需要人类授权。**

但如果两年内 Agent 的可靠性提升到"基本不需要人看"呢？那审阅层就没有市场了。

这个反驳很有力，但有两个地方站不住：

1. **可靠性提升不会消除审阅需求，只会转移审阅的粒度。** 就像编译器再可靠，代码仍然要 review——不是因为不信任编译器，而是因为"编译器不知道你想要什么"。Agent 越可靠，人类越会把更重要的决策交给它，而越重要的决策越需要人确认。
2. **责任无法转移给模型。** 出了事故，被追责的永远是人（CTO、开发者、公司）。只要责任在人身上，"人类确认"这个动作就不会消失，只会变得更轻量、更形式化。而"形式化的确认"恰恰是最适合做成产品的东西——它需要留痕、需要可审计、需要能证明"我真的看过了"。

所以更准确的判断是：**审阅不会消失，但会从"逐行看"退化成"看摘要 + 抽查 + 签字"。** 而这三件事，全部需要工具支撑。产品的形态会变（从 diff 视图变成异常摘要 + 风险抽样），但品类会一直在。
