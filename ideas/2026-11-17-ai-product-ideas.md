## 📊 今日核心洞察

### 一句话：能力层已经白菜价，贵的只剩"证明它是干净的"这一件事

今天的所有信号，指向同一个结构性变化。

**信号一：OPTIMJACK——15 家一线网站的源站是干净的，但访问者被抢了。**

安全研究者披露的这起事件值得完整复述：攻击者没有攻破 CNN、Zoom、Fox News、BBC、Salesforce、GitLab、American Eagle、Hootsuite 中的任何一家。他们攻破的是这些网站共同加载的 **Optimizely 实验标签**——也就是市场部门为了做 A/B 测试，在页面 `<head>` 里塞进去的那段第三方 JS。

投毒后的 bundle 里多了一行：动态创建 `<script src="https://1688360.cc/track.js">`。这个 track.js 干四件事：

1. **加密地址替换（clipper）**：正则 + 真实校验和（double-SHA256、base58check、bech32、cashaddr、TON CRC16），覆盖 ETH/BTC/SOL/TON/TRX/DOGE 等 8 条链。它不只改输入框，还改 DOM 文本（50ms 轮询、支付关键词触发）、改 `fetch`/`XHR` 的 URL 和 body、改 `navigator.share`、改剪贴板读写。用户复制的钱包地址，粘进去的那一瞬间就已经是攻击者的了。
2. **截图 + Cookie 外传**：页面 URL（≤500 字符）、Cookie（≤8000 字符）、html2canvas 截图，一起 POST 到 `/hit.php`。
3. **信用卡侧录**：Luhn + 卡组织校验、MM/YY + CVV 格式校验，钩住 `fetch`/`XHR` 的 POST body 和表单提交，`sendBeacon` 到 `/card.php`。
4. **iOS 二阶段**：仅 iPhone/iPad 注入 `boot.js`，从两个 `.icu` 域名拉下一层载荷。

最刺眼的一句是研究报告自己的总结：**"你的源站可以是干净的，但你的访问者照样被抢——投毒点在标签层。"**

这句话把过去十年的前端安全模型掀翻了。CSP、SRI、依赖扫描、SAST、渗透测试，全部围绕"我的代码"和"我的构建产物"展开。但现代网站的运行时，有一大半代码不是你的：分析、A/B 测试、客服挂件、广告、推荐、支付 SDK、字体、CDN。**它们在你的域名下、你的 CSP 白名单里、你的用户浏览器中执行，拥有和你的一线代码完全相同的权限，却不由你的 CI 管。**

而这条链路的分发权，掌握在少数几家 SaaS 手里。攻破一家，等于同时攻破几千个站点。OPTIMJACK 只是把这个杠杆效应演示了一遍。

**信号二：Hugging Face 和 OpenRouter 联手，开放权重模型变成"随手可跑"。**

同一天 HF 官方博客发布与 OpenRouter 的合作：在 HF 上看到的开放权重模型，可以直接在 OpenRouter 上一键调用，不必自己找 GPU、配 vLLM、折腾量化。

这件事的商业含义不是"又多了一个推理入口"，而是**模型层的分销渠道被彻底打通了**。以前一个开源模型从发布到被产品用上，中间隔着：找卡、装环境、测吞吐、比价格、做 fallback。现在是一行 API key。

结合 `llama.cpp v1.0.0` 的发布（本地 AI 生态终于有了一个稳定的 1.0 基线），以及 GitHub 日榜上 `ggml-org/ggml` 仍在榜——可以下一个判断：**推理正在变成和水电一样的基础设施，而且是双轨的（云上随手调 + 本地随手跑）。**

**信号三：GitHub 日榜第一名是"AI 办公套件 SDK"，不是模型。**

今天 Trending 第一是 `dream-num/univer`，一句话定位："用 Univer Office SDK 构建你自己的 AI 办公室——把编辑、计算、协作、文件处理带进你的产品，服务于人，也服务于 AI Agent。"

它后面还跟着一整套同方向的仓库：`ag-ui-protocol/ag-ui`（Agent 与用户界面的交互协议）、`google-labs-code/stitch-skills`、`backnotprop/plannotator`（昨天登顶的 Agent 审阅工作台，今天还在榜）、`ChromeDevTools/chrome-devtools-mcp`、`alibaba/open-code-review`、`NVIDIA/SkillEvaluator`。

**这张榜单几乎没有一个是"更强的模型"。全是"让 Agent 接入既有工作系统，并且让人能看懂它在干什么"的中间件。**

## 🔍 潜在需求分析

### 需求一：第三方标签层的"运行时完整性"——最贵的盲区，恰好是市场部管的

**痛点来源**

OPTIMJACK 暴露的不是一个新漏洞，而是一个长期存在的**责任真空**：

- 安全团队管代码仓库、管服务器、管 WAF，但 `cdn.optimizely.com/js/xxx.js` 不在他们的资产清单里；
- 市场团队管标签管理器、管 A/B 测试、管转化率，但他们不懂什么叫 SRI、什么叫 CSP；
- 法务和合规团队管隐私政策，但不知道页面上有 14 个第三方脚本在往外发数据。

三方都以为"这块不归我"。于是这块就成了攻击者最喜欢的地方——**权限最高（同源执行）、审查最少（不走 CI）、杠杆最大（一家供应商服务几千站点）。**

更现实的一层：很多公司连"我现在到底加载了哪些第三方脚本"都答不上来。标签管理器里套标签管理器，A/B 工具里再注入分析脚本，一个页面跑 30 个域名的请求是常态。**没有清单，就没有审计；没有审计，就没有告警。**

**具体场景**

一家年 GMV 5 亿的独立站电商，市场部用 Optimizely 做落地页实验，用三个分析工具，用两个客服挂件。某天早上，支付页的标签 bundle 被上游投毒。表现是：转化率微微下降（因为 clipper 让部分用户付款失败），客服收到几笔"我付了但没到账"的投诉，财务在两周后对账时发现异常。

整个过程中，**没有任何一个系统报警**。因为攻击没有触碰源站，没有触发 WAF，没有产生异常登录。唯一异常的是"转化率降了 0.3%"，而这在正常波动范围内。

这就是这类攻击最可怕的地方：**它的检测信号不在安全系统里，在业务指标里。**

**市场机会**

做"标签层供应链的持续监控"，切入点不是"更快的漏洞扫描"，而是三件更朴素的事：

1. **资产清点**：用真实浏览器跑你的页面，把所有实际执行的脚本按域名、大小、hash、权限列出来，形成一份"运行时 SBOM"。这份清单本身就是可以卖钱的东西——因为几乎没有公司有。
2. **变更告警**：对每个 served bundle 做 hash 与内容 diff。第三方 SDK 更新是正常的，但"bundle 里突然多了一段动态创建 script 的代码"永远不正常。这类规则可以做到很高精度。
3. **权限收缩**：自动生成并维护 CSP 的 `script-src` 白名单，把"所有第三方"从"默认信任"改成"逐个显式授权 + 违规上报"。报告里提到，有两家受影响站点就是因为 CSP 拦住而未执行——**这是唯一被验证有效的防线。**

定价上，这是一个典型的"按站点数 + 扫描频率"的订阅生意。中小电商愿意为"防止某天早上突然被薅走客户的钱"付月费，而且这类工具天然带合规叙事（PCI DSS 4.0 已经明确要求对支付页面的第三方脚本做完整性监控）。

### 需求二：给 Agent 一副"能操作表格、但改不坏"的手套

**痛点来源**

Univer 登顶不是偶然。过去半年，Agent 的能力边界从"写代码"扩到了"操作业务系统"，而业务系统里最普遍、最脏、最没有 API 的载体就是**表格和文档**。

一个真实的运营场景：让 Agent 每天早上读取供应商发来的 Excel 报价单，清洗格式，比对历史价格，更新到内部的价格表，然后生成一份变动摘要。这件事人做要 40 分钟，Agent 做只要 40 秒——但**没人敢让它直接写生产表格**。

原因很具体：

- 表格没有"事务"。写错一个单元格不会报错，只会让月底的报表差 3 万块。
- 表格没有"diff"。人改了什么，靠 undo 栈，关了文件就没了。
- 表格没有"权限粒度"。给 Agent 一个文件路径，等于给它整张表的写权限。
- 公式是图灵完备的。一个循环引用能让整个工作簿重算卡死。

所以企业的真实状态是：**Agent 在只读模式下很好用，一旦要写，就得有人盯着。** 这恰好抵消了 Agent 的价值。

**具体场景**

一家 200 人的贸易公司，财务用 Google Sheets 维护应收账款。想让 Agent 每天自动核对银行流水和应收明细，标记差异。技术上完全可行，但 CFO 的问题是三个："它改错了怎么办？""我怎么知道它改了什么？""出问题能不能退回去？"

这三个问题，现在没有产品能干净地回答。要么让人工复制一份副本跑（那不如人自己做），要么给 Agent 全权限（没人敢批）。

**市场机会**

做一个"Agent 表格/文档操作网关"，核心不是解析引擎（Univer、SheetJS、Luckysheet 已经够用），而是**把"写操作"变成可审计、可回滚、可审批的事务**：

- 拦截层：Agent 不直接拿到文件句柄，只能提交"操作意图"（改哪个 sheet、哪个区域、改成什么、依据是什么）。
- 语义 diff：把"单元格 A1 从 120 改成 118"翻译成"SKU-1234 的采购价从 120 下调 1.7%，依据是供应商 11/16 报价单"。
- 沙箱预演：先在副本上执行，跑一遍所有公式，检查是否产生 `#REF!`、`#DIV/0!`、循环引用、以及关键汇总行的偏移是否超过阈值。
- 分级放行：小额、低风险变更自动提交；超过阈值进人工审批队列（飞书/Slack 卡片，一键批准/驳回）。
- 回滚：每次提交是一个 commit，支持按行、按批次、按时间点回滚。

这个产品的定位很清晰：**不是"更好的表格 AI"，而是"让表格 AI 能进生产环境的那个阀门"。** 前者是工具，后者是基础设施，后者的定价权和粘性都高一个量级。

### 需求三：开放权重模型的"上架体检"——模型越多，选型越贵

**痛点来源**

HF × OpenRouter 打通之后，一个团队面对的选择从"三五个主流模型"变成了"每周新增几十个开放权重模型"。

结果不是"选择变多所以更好"，而是**决策成本指数上升**：

- 这个模型的许可证允许商用吗？（Apache 2.0 / Llama Community / 各种自定义条款，细则差别很大）
- 它的上下文是真的 128K，还是"标称 128K，32K 之后开始胡说"？
- 它的量化版本（GGUF Q4_K_M / AWQ / GPTQ）掉点多少？掉在哪些任务上？
- 它的 tokenizer 和 chat template 有没有坑？为什么同一个 prompt 在 vLLM 和 llama.cpp 上输出不一样？
- 它的安全对齐程度如何？会不会在特定语言下突然输出不该输出的东西？

这些问题，现在只能靠人肉试。**每个团队都在重复做同一份调研，而且做完就过期。**

**具体场景**

一家做垂直行业 SaaS 的公司，想把一个 8B 模型私有化部署到客户机房。工程团队花了两周，试了 6 个候选模型、3 种量化、2 个推理框架，写了一份内部评测报告。三个月后，客户问"有没有更新的模型"，一切重来。

这两周里，真正有价值的判断可能只有三句话。剩下 90% 的时间花在：找评测集、跑 benchmark、对齐环境、整理结果。

**市场机会**

做"模型上架前的体检报告"——输入一个 HF repo id，输出一份结构化报告：

- **许可证**：机器可读的商用条款摘要 + 红旗项（比如"禁止用于竞争产品"）。
- **能力**：在一组标准化任务上的实测分数（不是抄榜单，是自己跑），特别标注"标称上下文 vs 有效上下文"的衰减曲线。
- **量化损失**：同一模型在 FP16 / Q8 / Q4 / Q3 下的分数差，给出"性价比拐点"建议。
- **工程坑**：chat template、特殊 token、已知 issue、推荐推理参数。
- **安全基线**：在标准红队集上的通过率。

商业模式可以是"报告订阅"（每周新增模型自动出报告）+ "私有化评测"（客户自己的数据集）。壁垒不在模型，在**评测流水线的工程质量和历史数据的连续性**——做得越久，越能回答"这个模型相比三个月前那版到底好了多少"。

### 需求四（补充）：AI 批量写信时代的送达率合规

Spamhaus 11 月的新发信人要求，撞上了 AI 让"批量个性化邮件"成本归零这件事。

以前发 10 万封邮件需要一个团队；现在一个销售用 AI 半小时能生成 10 万封"看起来像手写"的邮件。结果是**全行业的邮件信誉在被稀释**——Gmail、Outlook 的反垃圾阈值只会越来越严，Spamhaus 这类组织的准入只会越来越高。

中小企业的真实痛点：他们不知道自己的域名有没有配 SPF/DKIM/DMARC，不知道自己的发信 IP 有没有进黑名单，不知道"打开率突然掉一半"是因为进了 promotions 还是进了垃圾箱。而一旦被拉黑，恢复要以周计。

这里的机会不是"又一个邮件营销工具"，而是**"发信前的体检 + 发信中的信誉监控"**：域名认证检查、黑名单监控、种子邮箱投放测试（seed testing）、按收件域统计的进箱率。这是一个安静、刚需、按发送量计费的好生意。

## 🚀 新产品创意

### 创意一：TagProof —— 前端第三方标签层的"运行时 SBOM + 变更防火墙"

**产品定位**

面向中大型电商、媒体、SaaS 的**标签供应链安全平台**。一句话：*把你的页面上所有不是你自己写的 JS，变成一份可查询、可告警、可拦截的资产清单。*

不叫"安全扫描器"，叫"标签层的包管理器"——因为它的核心心智是**依赖治理**，而不是漏洞检测。这个定位差异很重要：前者是买一次的工具，后者是每月付的订阅。

**核心功能**

1. **真实浏览器采集（Runtime Census）**
   用 headless Chromium 在隔离环境里加载客户的每一个关键页面（首页、商品页、支付页、登录页），记录所有实际执行的脚本：域名、完整 URL、内容 hash、字节数、首次发现时间、执行时长、发起者（是哪个脚本又加载了它）。同时记录所有出站请求的域名与 payload 大小。

   输出的东西长这样：

   ```
   页面 /checkout
   ├─ cdn.optimizely.com/js/5113954737848320.js  (142KB, sha256:9f3a…)
   │  └─ 1688360.cc/track.js                     ⚠️ 未知域名，首次出现 2 小时前
   ├─ connect.facebook.net/en_US/fbevents.js     (98KB)
   └─ ...
   ```

   关键点：**它抓的是"实际执行的"，不是"代码里写了什么"。** 这一条就把静态扫描类工具全比下去了。

2. **四类变更规则**
   - 新增外部域名（最危险，默认告警）
   - bundle 内出现 `document.createElement('script')` / `eval` / `atob` + 动态域名拼接
   - 脚本权限扩大（开始读 clipboard、开始访问 input value、开始 hook fetch/XHR）
   - 同一 vendor 的 bundle hash 在非发布窗口发生变化

3. **CSP 生成与渐进式收缩**
   从实际流量学习一份 baseline CSP，先以 `Content-Security-Policy-Report-Only` 模式跑两周，收集违规，再逐域名收紧成强制模式。这是唯一被 OPTIMJACK 事件验证有效的防线——报告里有两家站点正是被 CSP 拦下。

4. **业务指标关联**
   把"标签变更时间点"和"转化率、支付成功率、跳出率"叠在同一张时间轴上。安全告警没人看，但"昨天下午 3 点支付成功率掉了 2%"一定有人看。

**技术实现**

- 采集层：Playwright + 定制的 CDP 监听（`Network.responseReceived` + `Debugger.scriptParsed`），记录脚本来源链。关键是**保留 initiator 链**，才能回答"这个恶意脚本是谁带进来的"。
- 存储：脚本内容按 hash 去重存对象存储，元数据进 Postgres（`script`、`page`、`load_edge`、`domain` 四张表）。
- 检测：规则引擎 + 一个小的分类模型（判断 bundle 是否"像被注入了 loader"）。规则优先，模型只做排序，避免误报把用户训练成"忽略告警"。
- 报告：每日邮件摘要 + Slack/飞书告警 + 面向审计的 PDF（PCI DSS 4.0 的 6.4.3 和 11.6.1 正好要求这个）。

**MVP 范围（6-8 周）**

- 只做 5 个页面/站点，每天扫一次
- 只做"新增域名"和"hash 变更"两类告警
- 只出 CSP Report-Only 建议，不做自动下发
- 单一通知渠道（Slack webhook）

不做：不做 WAF、不做运行时阻断（JS 层阻断误杀率太高）、不做移动 App。

**定价策略**

- **Starter** $99/月：3 个站点、每日扫描、邮件告警
- **Growth** $499/月：20 个站点、每小时扫描、Slack 告警、CSP 建议、PCI 报告
- **Enterprise** $2k-8k/月：不限站点、实时监控、私有部署采集节点、SSO、审计日志

获客路径：先做一份"免费标签清单"作为 lead magnet——输入域名，10 分钟给你一份"你的支付页现在加载了 23 个第三方脚本，其中 4 个来自你市场部不知道的域名"。这个钩子的转化率会很高，因为**大多数公司看完这份清单的第一反应是"我们居然加载了这个？"**

**风险**

- 大客户会问"你能不能直接帮我阻断"——需要明确边界，做监控和告警，不做 inline 阻断。
- 标签管理器厂商可能自己做（Google Tag Manager 有类似能力），但它们不会做"跨厂商"的审计，中立第三方是价值所在。

### 创意二：LedgerGate —— Agent 写表格的"事务层"

**产品定位**

面向把 AI Agent 接入财务、运营、供应链流程的团队，提供一层**表格/文档写操作的网关**。一句话：*让 Agent 能改表，但改的每一步都有 diff、有审批、有回滚。*

类比很好找：**Git 之于代码，LedgerGate 之于表格。** 这个类比可以直接用在落地页上，因为目标客户（技术负责人 + 财务负责人）都听得懂。

**核心功能**

1. **操作意图协议（Intent Protocol）**
   Agent 不拿文件句柄，只能提交结构化意图：

   ```json
   {
     "target": "sheet://ar-2026/应收明细",
     "op": "update_range",
     "range": "D120:D148",
     "values": [...],
     "reason": "根据 11/16 银行流水核对，标记 3 笔到账",
     "evidence": ["file://bank/2026-11-16.csv#rows:44,51,77"],
     "idempotency_key": "recon-2026-11-16-v1"
   }
   ```

   `reason` 和 `evidence` 是必填的。这一条设计看似麻烦，实际是整个产品的灵魂：**它强迫 Agent 留下"为什么改"，而这正是人类审计时最想知道、也最难事后还原的东西。**

2. **语义 diff 渲染**
   不是显示"A1: 120 → 118"，而是：

   > 第 120 行 SKU-4471「304 不锈钢法兰」采购单价 120.00 → 118.00（-1.67%）
   > 依据：供应商 A 11/16 报价单第 7 行
   > 影响：本行金额 24,000 → 23,600；本月采购合计 -1,240（-0.8%）

   技术上靠"表头 + 主键列"推断语义，配合客户配置的字段字典。

3. **沙箱预演与不变量检查**
   在副本上执行 → 全量重算 → 检查：
   - 公式错误（`#REF!` `#DIV/0!` `#N/A`）
   - 循环引用
   - 关键汇总指标的偏移超出阈值（比如"本月合计变动 > 1%"就拦）
   - 主键重复、必填为空、类型不符

4. **分级放行策略**
   按"金额影响 × 单元格数量 × 是否触及受保护区域"打风险分：
   - 低风险 → 自动提交，进 digest
   - 中风险 → 审批队列（飞书卡片，展示语义 diff，一键批/驳）
   - 高风险 → 强制双人审批 + 冷却期

5. **不可变审计账本**
   每次提交是一条 append-only 记录，包含：意图、diff、证据、审批人、执行结果、前后快照 hash。支持按行、按批次、按时间点回滚。导出即审计报告。

**技术实现**

- 表格引擎：Univer（开源、支持协同、有完整公式引擎）做本地计算与渲染；读取侧兼容 xlsx / Google Sheets / 飞书表格。
- 沙箱：每个 workspace 一个容器，表格副本 + 公式重算，跑完丢弃。
- Diff：单元格级 + 语义级双层。语义层靠"字段字典 + 主键推断"，不追求全自动，允许客户标注。
- 存储：每次提交存完整快照（压缩后 xlsx 很小）+ 反向 patch，回滚 O(1)。
- Agent 接入：MCP server 暴露 4 个 tool（`propose_change` / `preview` / `commit` / `rollback`），这样 Claude Code、Codex、任何支持 MCP 的 Agent 都能直接接。

**MVP 范围（8-10 周）**

- 只支持 xlsx 和飞书表格
- 只支持"区域更新"一种操作（覆盖 80% 的实际需求）
- 只做"金额阈值"一种风险策略
- 审批只接飞书
- 不做多人协同编辑（读时加锁即可）

**定价策略**

- **Team** $29/seat/月：5 个 workspace、每月 1000 次提交、飞书审批
- **Business** $199/月 + $0.02/次提交：不限 workspace、自定义风险策略、审计导出、MCP 接入
- **Enterprise** 年费 $30k 起：私有部署、SSO、对接内部审批流、SLA

真正的收费点不是 seat，是**"提交次数"**——因为提交次数直接对应"你有多大比例的业务跑在 Agent 上"，这个数字会随客户成功而自然增长。

**为什么现在做**

三个条件同时成熟了：Agent 真的能可靠地操作结构化数据了；Univer 这类开源引擎把表格内核商品化了；企业对"AI 改生产数据"的恐惧到达了顶点。**恐惧是最好的销售。**

**风险**

- 飞书/钉钉/Notion 可能自己做类似能力——所以要快，且要中立（跨平台是护城河）。
- 客户可能觉得"我让人工复核就行"——需要用数据打：一次人工复核 40 分钟，一次 LedgerGate 审批 40 秒。

### 创意三（轻量备选）：ModelDossier —— 开放权重模型的"体检报告"

**定位**：给每个 HF 模型出一份可信的、可对比的、会过期的体检报告。定位是"模型选型的 Consumer Reports"。

**核心功能**：许可证机器可读摘要 / 实测能力分（自建评测集）/ 量化损失曲线 / 有效上下文衰减测试 / 工程坑清单 / 安全基线。

**技术实现**：评测流水线（vLLM + llama.cpp 双后端，保证结果可比）+ 自动化 harness + 报告生成。难点不在模型，在**评测集的设计和持续维护**——这也是唯一能形成壁垒的地方。

**MVP**：每周挑 10 个当周最热的开放权重模型，跑固定 8 个任务，出对比表，公开发布。先用内容获客（"本周 10 个新模型，只有 2 个值得试"），再卖订阅。

**定价**：公开报告免费；Pro $49/月（全量历史 + API）；企业私有评测 $5k/次起。

**判断**：这个方向的短期变现不如前两个，但**内容杠杆极高**——每一份报告都是一篇天然的传播素材，适合作为前两个产品的流量入口。

## 🧭 趋势判断与行动建议

### 三个判断

**判断一：2026 年 H2 的主战场是"信任层"，不是"能力层"。**

今天的四条主线——标签层投毒、开放权重商品化、本地推理 1.0、Agent 办公件——看起来互不相关，但它们共享同一个结构：

> 供给端（模型、脚本、SDK、数据）变得极其便宜、极其分散、极其自动化；
> 需求端的瓶颈从"能不能做到"变成了"能不能确认这个做到的东西是可信的"。

这解释了为什么 GitHub 榜单上全是中间件：Plannotator（审代码）、ag-ui（人机交互协议）、chrome-devtools-mcp（让 Agent 操作浏览器）、open-code-review（自动化审查）、SkillEvaluator（评估技能质量）。**没有一个是"更强的模型"，全是"让人能验收"的装置。**

推论：未来 12 个月，最值得做的产品不是"又一个 AI 应用"，而是"某个 AI 应用进入生产环境前必须经过的那道门"。

**判断二：安全产品的买家正在从 CISO 变成 CMO 和 CFO。**

OPTIMJACK 的受害者不是被攻破的网站，是访问者。赔付、声誉、监管压力最终落到业务侧。而标签层的实际控制权在市场部手里。

这意味着新的安全产品必须**说业务语言**：不说"检测到供应链投毒"，说"你的支付页转化率掉了 2%，原因是第三方脚本被篡改"。不说"CSP 违规",说"这 4 个脚本能读用户的剪贴板，其中 3 个你市场部不认识"。

**判断三：Agent 的落地瓶颈是"写入权限"，不是"理解能力"。**

现在所有 Agent 演示都在只读场景里跑：读代码、读文档、查数据、给建议。一旦要写——改表、发邮件、下单、改配置——立刻卡住，因为**没有事务、没有 diff、没有回滚、没有审批流**。

这是一个巨大的产品空档。谁能把"写操作"工程化，谁就能让 Agent 从 demo 走进生产。LedgerGate 是这个方向的一个具体形态，但同样的逻辑适用于：Agent 改配置（Kubernetes、Terraform）、Agent 发邮件、Agent 动财务系统。

### 如果只做一件事

**做 TagProof 的免费标签清单。**

理由很实际：

1. **它是最短的验证路径**。不需要客户接入 SDK、不需要改代码、不需要审批采购——给个域名就能出结果。
2. **它的输出自带冲击力**。一份"你的支付页加载了 23 个第三方脚本，其中 4 个来自未知域名"的报告，比任何 pitch deck 都有说服力。
3. **它天然指向付费**。清单是静态的，但脚本每天都在变——看完清单的人下一个问题必然是"那我怎么知道明天变了没有"。

具体做法：花一个周末写个 Playwright 脚本，抓 20 个目标客户的支付页，生成 20 份报告，冷邮件发出去。转化率会告诉你这个市场是不是真的。

### 今日可复用的三个数字

- **15**：OPTIMJACK 波及的一线网站数量（CNN、Zoom、Fox News、BBC、Salesforce、GitLab、Hootsuite…）。用来向客户说明"这不是小站才会中招"。
- **8**：被 clipper 覆盖的区块链数量（ETH/BTC/SOL/TON/TRX/DOGE/BCH/LTC）。用来说明攻击者的工程化程度。
- **0.3%**：一次标签投毒可能造成的转化率下降幅度——小到不会触发任何告警，大到足以让一个月利润消失。这是"为什么需要持续监控"最好的论据。
