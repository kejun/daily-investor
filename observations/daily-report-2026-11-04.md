### 16.1 数据基建启发（数据库/容量规划视角）

本周的数据基建信号集中在"成本曲线"而非"新架构"：AI 投入端估值被系统性下修（半导体 −3.13%、AI 电力 −10%+），本质是市场开始质疑"每美元算力投入的边际回报"，这直接对应到数据侧的**单位存储与检索成本必须继续下降**的硬约束。当推理成本下行、agent 应用平民化，最先爆炸的不是模型参数而是**副产物数据**：agent 会话轨迹（每次任务数百轮 tool call 的完整日志）、向量化的检索语料、以及用于回放的时序事件流。这类数据的特征是"写多读少、按时间分区、需要按 session 聚合"，与传统 OLTP 的随机读写模式完全不同。

选型上的具体判断：① **向量检索正在下沉到主库**——PostgreSQL + pgvector / pgvectorscale 已能承载千万级向量的 HNSW 查询，独立向量库的边际优势只剩超大规模（>1 亿向量）与多租户隔离场景，中型团队引入独立向量引擎的运维成本已高于收益；② **OLAP/OLTP 边界重新变模糊**——agent 轨迹的"写入即分析"需求（实时算成功率、token 成本、工具调用分布）让 ClickHouse/Doris 这类列存开始承接原本属于 OLTP 的写入流，TiDB/PostgreSQL 的 HTAP 路线在此场景重新有说服力；③ **缓存分层成为成本主战场**——prompt cache（前缀缓存）+ 语义缓存 + KV cache 三层叠加，能把重复检索的向量查询打掉 60% 以上，这比换数据库更省钱；④ **数据湖仓的角色变为"冷轨迹归档"**——Parquet + Iceberg 承接 30 天以上的会话存档，热数据留在行存，冷热分层是唯一能把 PB 级 agent 日志成本压到可接受区间的方法。

容量规划上最容易被忽略的一点：**agent 会话是"长事务 + 大对象"**，单 session 的 JSON 轨迹可达数 MB，用关系表逐条存会产生严重的行膨胀与 vacuum 压力，正确做法是"元数据入行存、payload 入对象存储 + 指针回填"。这一条在 2026 年的实践中已反复验证：凡是把完整 tool output 塞进 TEXT 列的系统，最终都撞上 autovacuum 与 TOAST 的性能墙。
