### 16.1 数据基建启发（数据库 / 容量规划视角）

**数据规模与容量规划信号**：本周最值得数据库工程师注意的信号是**"推理成本下降 → 数据体积非线性膨胀"**。当 AI 应用（如当日暴涨的 SNOW/DDOG/PLTR）真正上量，其副产品是海量**可观测性数据 + 会话轨迹 + 向量嵌入**：每一次 Agent 交互都会产生多轮 tool-call 日志、prompt/response 轨迹与检索命中记录。这直接推高了三类存储压力：①**列存 OLAP**（日志/指标聚合）；②**向量索引**（embedding 检索）；③**OLTP 会话库**（Agent 状态与记忆持久化）。容量规划上，需要把"每用户每天问答数 × 平均 token × 轨迹保留期"纳入存储预算模型，而非只算业务主数据。

**存储与数据库选型思考**：趋势是**向量引擎与主库的融合**。传统"独立向量数据库 + 关系库"的双写架构，正被"**主库内建向量索引 + 混合检索（hybrid search）**"取代（Postgres/pgvector、MySQL 向量扩展、云原生 HTAP 引擎）。OLAP 与 OLTP 的边界也在模糊：Agent 的"实时检索 + 分析型聚合"要求同一系统既能低延迟点查，又能对轨迹做列存扫描。数据湖仓（Iceberg/Delta）开始承担"归档轨迹 + 训练数据回流"的角色，流式处理（Kafka/Flink）则位于"AI 数据面"的入口，负责把交互事件实时写进特征库与向量库。

**对数据库/前端的工程启示**：具体到技术名词与架构选择——①**索引侧**：向量索引（HNSW/IVF-PQ）需与 B-tree 索引共存，规划**混合检索**的查询规划器；②**存储侧**：引入**缓存分层**（热会话内存 → 温数据 SSD → 冷轨迹对象存储/湖仓），控制单位推理成本；③**可用性侧**：Agent 会话存储是"有状态服务"，需要**多副本 + 幂等写入**，避免工具调用重放导致的轨迹污染；④**成本侧**：向量维度与索引精度（PQ 压缩率）是直接的容量-精度权衡旋钮。整体而言，**AI 应用的爆发本质是一场数据基建的容量与架构压力测试**——谁能用更低成本存下更多轨迹并更快检索，谁就能在 Agent 时代取得工程优势。
